# 跨模块执行与回写规范

## 一、目的

爽律 Skill 的多个能力不是彼此独立的“功能菜单”。在复杂法律任务中，材料审阅、事实建模、问题构造、法律研究、证据分析、论证、策略比较、对抗性审查和最终文书应当通过结构化对象连续传递，并允许后一步发现的新信息回写前一步。

本规范解决两个问题：

1. **交接不断链**：上一步已经确认的事实、问题、来源和限制，不在下一模块中重新猜测；
2. **新发现能回写**：新规则、新案例、新证据或反方观点足以改变原判断时，必须更新受影响对象，而不是只在报告末尾补一句提示。

## 二、标准对象链

复杂任务原则上按实际需要形成下列对象链，不要求简单任务机械生成全部对象：

```text
MaterialRecord / SourceCard
        ↓
StructuredReviewRecord
        ↓
FactRecord ↔ EvidenceItem
        ↓
IssueRecord
        ↓
ResearchRequest
        ↓
ResearchResult
        ↓
LegalRule / CaseCard / SourceCard
        ↓
ArgumentRecord
        ↓
Finding
        ↓
OptionRecord / DecisionRecord（需要策略选择时）
        ↓
AdversarialReviewRecord（重要任务）
        ↓
Finding / Argument 回写修正
        ↓
DeliverableClaim
```

对象之间必须通过稳定 ID 或同等可回查关系连接。不得依赖“模型应该记得前面说过什么”作为模块交接机制。

## 三、结构化审阅到事实、证据和问题

结构化审阅不是终点。完成材料审阅后，应根据任务把记录拆分、合并或关联为：

- `FactRecord`：材料能够支持、反驳或影响的事实命题；
- `EvidenceItem`：用于证明或反驳待证命题的证据对象；
- `IssueRecord`：事实、证据、法律或策略上真正需要解决的问题。

一份材料可以支持多个事实；一个事实也可以由多份材料共同支持。不得为了表格整齐强迫一对一关系。

## 四、业务技能与法律研究双向交接

### 1. 发起研究

业务技能遇到以下情形时，创建 `ResearchRequest` 或同等结构：

- 需要核验现行法律规则；
- 概念边界、例外或特别规则不清；
- 需要类案比较；
- 存在相反观点或规则冲突；
- 当前结论对某一法律问题高度敏感。

研究请求至少说明：

- 对应哪个 `IssueRecord`；
- 具体要回答什么；
- 法域和关键时间；
- 需要的来源类型；
- 需要寻找的支持、反向、边界或例外材料；
- 什么结果足以回答当前业务问题。

### 2. 研究结果回填

法律研究返回的不是一段孤立说明，而应尽量回填：

- `LegalRule`；
- `CaseCard`；
- `SourceCard` / `SourceLocator`；
- `ResearchResult`；
- 对原 `IssueRecord` 的状态影响；
- 对已有 `ArgumentRecord` / `Finding` 的影响。

如果研究结果与原假设冲突，必须创建回写记录，重新检查受影响的事实问题、争点、论证和策略。

## 五、推理方法动态触发

爽律 Skill 不要求每个任务机械执行全部分析方法。Agent 应根据问题性质选择必要方法，并在论证记录中说明所采用的方法。

典型触发关系：

| 情形 | 优先考虑的方法 |
|---|---|
| 明确构成要件与案件事实对应 | 涵摄 / 演绎 |
| 案例事实相近但不完全相同 | 类比 + 区别 |
| 多份案例需要总结共同规则或事实模式 | 归纳 |
| 同一证据可以支持多个事实解释 | 竞争解释 / 溯因比较 |
| 需要判断某事实是否真正决定结论 | 反事实测试 |
| 需要主动寻找能推翻当前模型的信息 | 证伪测试 |
| 存在多个行动方案 | 选项比较 |
| 存在规则冲突、例外或边界 | 体系解释 / 特别规则检查 |

方法名称不是装饰。重要任务中，如记录采用某方法，应留下可以复核的理由摘要或中间对象。

## 六、选项树与策略比较

当法律上存在多个可行行动，而选择会影响权利、程序、成本、证据、谈判或后续空间时，应建立 `OptionRecord` 或同等方案比较对象。

每个重要选项至少记录：

- 选项内容；
- 成立或可执行前提；
- 支持该选项的事实和法律；
- 主要收益；
- 主要风险；
- 对方或机关可能反应；
- 所需补充信息或行动；
- 哪个事实、规则或外部条件变化会改变该选项评价。

比较时尽量使用相同维度，不得通过给偏好方案增加优点、给其他方案只列缺点制造结论。

涉及 C 级事项时，Agent 只能分析并形成 `DecisionRecord`，不得替用户作最终决定。

## 七、对抗性审查必须回写

重要任务形成初步 `Finding` 后，对抗性审查应冻结初步判断并形成 `AdversarialReviewRecord`。

审查发现实质问题后，必须出现以下结果之一：

1. 修订原 `ArgumentRecord` / `Finding`；
2. 降低结论确定程度或增加限制；
3. 新增材料、研究或人工决策任务；
4. 记录“维持原结论”的明确理由，并说明为什么反方不足以改变结论。

禁止出现：

> 对抗审查发现重大漏洞，但原结论、风险等级和交付文本完全不变，也没有任何解释。

## 八、回写事件

当后续信息实质影响上游对象时，用 `WriteBackEvent` 或同等方式记录：

- 触发原因；
- 新增或变化的信息；
- 受影响对象；
- 实际修改的对象；
- 哪些对象经过复核但无需修改；
- 是否需要重新执行研究、对抗审查或质量门控。

常见触发：

- 新材料改变事实状态；
- 证据来源或真实性发生变化；
- 新法律规则改变适用路径；
- 类案揭示新的决定性事实；
- 对抗性审查发现关键漏洞；
- 用户改变目标或接受不同风险；
- 人工决定改变后续策略。

## 九、人工决策节点

需要人工决定时，不能只输出“请律师判断”。应形成 `DecisionRecord`，至少包括：

- 需要决定的具体问题；
- 权限等级；
- 可选方案；
- 当前推荐（如允许给出）；
- 推荐所依赖的事实、法律和假设；
- 每个方案的主要后果；
- 仍缺什么信息；
- 用户/律师最终决定；
- 决定后需回写哪些对象。

未解决的 C/D 级节点仍按《人工决策与升级矩阵》阻断自动继续。

## 十、完成条件

复杂或重要任务至少应满足：

- 核心材料已进入可追溯的材料/审阅结构；
- 核心事实、证据和问题已经建立关联；
- 需要研究的问题已经有明确研究请求和结果回填；
- 重要论证能够回到规则、事实、证据和来源；
- 需要策略比较时已经形成可比选项；
- 对抗性审查发现的问题已经回写；
- 需要人工决定的事项已明确停点；
- 最终重要命题能够回到修订后的上游对象。

## 十一、禁止模式

- 每个模块各自输出一篇长文，彼此没有结构化交接；
- 法律研究完成后不更新业务争点和论证；
- 新证据出现后仍沿用旧事实状态；
- 对抗性审查只追加一段反方观点，不修改受影响结论；
- 为了“自动化”在没有依据时自动生成策略结论；
- 用关键词、脚本分值或模型自报置信度替代律师判断；
- 把未解决的人工节点隐藏在最终文书里继续自动执行。

## 新增公共工作对象

复杂跨模块任务可进一步交接 `TaskProfile / MatterWorkingModel / IssueTree / ReviewQuestionSet / AuthorityMap / CaseMatrix / ArgumentMap / PlanReviewRecord`。这些对象只用于稳定传递当前任务状态；若后续结果改变其内容，应通过 WriteBackEvent 更新，而不是让下一模块重新从自然语言摘要猜测。
