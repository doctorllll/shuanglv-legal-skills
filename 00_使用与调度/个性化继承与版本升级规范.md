# 个性化继承与版本升级规范

## 一、目标

爽律 Skill 的版本升级应当优先增加能力、修复缺陷，而不是把已安装用户长期形成的合法工作习惯重置为新版默认值。

本规范建立 `Personalization Layer｜个性化继承层`。核心原则是：

> **Core 可升级，Personalization 默认继承；遇到冲突时先保留、再解释、再由用户决定。**

但个性化不得覆盖事实核验、法律准确性、敏感数据外发授权、人工最终决定等不可放弃的核心边界。

## 二、四级优先级

同一事项出现多个设置时，按下列顺序解析：

```text
Hard Guardrails｜不可覆盖硬规则
        ↓
Matter Override｜事项/案件特殊设置
        ↓
User Personalization｜用户个性化
        ↓
Version Defaults｜当前版本默认设置
```

其中：

- `Hard Guardrails`：事实状态、法律核验、安全、隐私、外部处理授权、人工决定等核心规则；
- `Matter Override`：某案件、客户或项目的特殊工作要求；
- `User Personalization`：用户长期稳定的写作、交付、分析展示和调用习惯；
- `Version Defaults`：爽律 Skill 当前版本针对新用户的推荐默认行为。

## 三、个性化不得直接修改 Core

用户个性化应保存在独立的 **爽律用户空间**，不得通过直接改写 Core 文件实现。

推荐目录：

```text
工作目录/
├─ 爽律Skill/                    # 可整体替换的 Core
└─ 爽律用户空间/                 # 升级默认保留
   ├─ user-profile.json          # 用户个性化档案
   ├─ matters/                   # 事项/案件级设置
   ├─ custom-rules/              # 用户自有规则
   ├─ custom-templates/          # 用户自有模板
   ├─ snapshots/                 # 升级/重置前快照
   ├─ migrations/                # 升级迁移报告
   └─ legacy-customizations/     # 从旧 Core 中识别出的历史自定义
```

平台无法提供持久文件目录时，应使用“导出个性化包 → 升级 → 导入个性化包”的方式迁移，不能假装存在长期持久化。

## 四、个性化设置的来源

一个设置只有在以下情形才可进入 `ACTIVE`：

1. 用户明确说“以后默认……”“以后不要……”“我习惯……”“保留这个设置”等；
2. 用户主动导入已有个性化档案；
3. 版本升级从旧用户空间迁移而来。

仅根据单次行为、语气或模型推断得到的偏好，不得静默激活。此类内容最多进入 `SUGGESTED`，待用户确认后再启用。

## 五、设置项状态

- `ACTIVE`：当前生效；
- `DISABLED`：用户暂时关闭，但保留历史；
- `SUGGESTED`：系统观察到可能的习惯，尚未确认，不生效；
- `DEPRECATED`：旧版本设置已被更合适的新设置替代；
- `ORPHANED`：新版已找不到对应能力，保留在档案但不生效；
- `BLOCKED_BY_GUARDRAIL`：与不可覆盖硬规则冲突，保留记录但禁止生效。

## 六、升级默认策略

升级默认策略为 `PRESERVE_USER`：

- 新功能：加入 Core，但不覆盖已有用户设置；
- 用户模板资产：继续保存在爽律用户空间；新版系统模板不得静默覆盖、替换或删除用户已有模板；
- 默认值变化：新用户采用新版默认；老用户继续保留自己的显式设置；
- 设置重命名：有迁移映射时自动迁移；
- 设置废弃：保留原记录并标记 `ORPHANED/DEPRECATED`，不得静默删除；
- 与硬规则冲突：禁止继续生效，并在迁移报告中说明原因；
- 无法自动判断：标记 `REVIEW_REQUIRED`，由用户决定。

用户可主动选择：

- `PRESERVE_USER`：保留个人设置（默认）；
- `ADOPT_NEW_DEFAULTS`：对可覆盖项采用新版默认；
- `REVIEW_ALL`：逐项查看再决定。

## 七、版本变化分类

每次版本升级应对变化标记：

- `CORE_FIX`：错误修复；
- `CORE_CAPABILITY`：新增能力；
- `DEFAULT_CHANGE`：默认行为改变；
- `BREAKING_CHANGE`：旧行为无法继续兼容。

`DEFAULT_CHANGE` 不得成为清除老用户个性化的理由。`BREAKING_CHANGE` 必须提供迁移说明、影响项和回滚路径。

## 八、升级流程

```text
读取旧版本与用户空间
→ 建立升级前快照
→ 读取新版本迁移清单
→ 识别用户设置 / 事项设置 / 历史 Core 修改
→ 计算可自动迁移项
→ 识别冲突与失效项
→ 默认保留可兼容个性化
→ 生成 UpgradeMigrationReport
→ 仅对必要冲突要求用户决定
→ 写入新档案
→ 保留回滚快照
```

如果旧用户曾直接修改 Core，升级助手应在能够取得旧版官方基线时做 Hash 比较，把差异识别为 `legacy customization candidate`；不能把旧版 Core 的所有文件都当成个性化。

## 八A、模板资产迁移

用户模板与个性化设置同样适用 `PRESERVE_USER`。升级 Core 时不得进入 `custom-templates/`；跨环境导入同名/同路径模板时默认保留当前用户资产。用户可以显式选择采用传入版本，但该决定应记录在迁移报告中。模板的识别、选择和成套交付规则见《模板资产与成套交付规范》。

## 九、个性化管理

用户可随时要求：

- “列出我的爽律个性化设置”；
- “关闭这条设置”；
- “恢复这一项为新版默认”；
- “只保留文书风格设置”；
- “导出我的爽律个性化”；
- “检查哪些设置已经没有必要”；
- “恢复到本次升级前”。

系统应优先展示**当前生效设置、来源、作用范围、是否覆盖新版默认、是否存在冲突**，不要向普通用户暴露内部 Schema 细节。

## 十、个性化体检

长期使用后可形成 `Personalization Health Check`：

- 长期未触发项；
- 与新版默认已完全一致的冗余项；
- 多条相互矛盾的设置；
- 已废弃/孤儿设置；
- 仍处于 `SUGGESTED` 的未确认项；
- 与当前核心能力冲突的设置。

体检只提出清理建议，不得未经用户确认删除 `ACTIVE` 设置。

## 十一、边界

本层不是用户画像数据库，也不要求爽律 Skill 自建长期记忆服务。

不得在用户级个性化档案中长期保存具体案件事实、证据原文、客户秘密或不必要的敏感信息。事项级信息应放在受控的 `MatterProfile` 或用户自己的项目空间中。

平台已有的长期记忆、系统级偏好或外部配置若没有提供可读取/导出的接口，爽律 Skill 不能自动恢复；只能在平台提供数据后导入，不能假装已经迁移。


## 十二、v0.43 激活偏好继承

自动激活属于可个性化行为，不属于不可覆盖硬规则。新用户默认 `activation.mode=AUTO`，但已安装用户一旦明确选择 `AUTO / CONFIRM / MANUAL`，后续升级必须按 `PRESERVE_USER` 保留。

`activation.show_notice=false` 只控制是否显示“已调用爽律”等提示，不降低事实/法律/来源透明度。`MANUAL` 只关闭无感自动激活，不关闭用户显式说“调用爽律”后的能力。

用户模板、文书习惯、研究报告格式等既有个性化与激活偏好相互独立；升级 v0.43 不得借“Agent Native”之名清空或重置这些资产。
