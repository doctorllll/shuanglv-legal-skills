# 模板资产与成套交付规范

## 一、目的

爽律 Skill 处理的对象应当优先理解为“律师要完成的一项任务”，而不只是“生成一个文件”。当同一任务需要多份相互关联的文书、表格、目录或说明时，应建立 `DeliverableBundle｜成套交付包`；当多个交付物共享主体、日期、金额、请求、合同信息或其他基础数据时，应建立 `SharedMatterFields｜共享事项字段`，避免每份文件分别猜测、重复录入和彼此漂移。

与此同时，用户自己的模板和长期习惯属于其个性化资产。版本升级不得把系统新模板静默替换为用户已有模板，也不得因为新增默认流程而清除用户已经明确确认的写作、格式或交付习惯。

核心原则：

> **系统默认可以升级，用户资产默认保留；任务可以成套完成，但共享信息必须可追溯、可回写、可复核。**

## 二、模板资产层与个性化的关系

`Template Asset Layer｜模板资产层` 是 Personalization Layer 的资产子层。模板文件本身不写入 Core，而保存在独立“爽律用户空间”中；Core 只定义如何识别、选择、使用、迁移和校验模板。

推荐结构：

```text
爽律用户空间/
├─ user-profile.json
├─ template-assets.json          # 模板资产清单
├─ custom-templates/             # 用户长期模板
├─ matters/                      # 案件/项目级设置与模板引用
├─ custom-rules/
├─ snapshots/
├─ migrations/
└─ legacy-customizations/
```

模板可来自用户上传、用户明确确认、旧版本迁移或当前事项指定。任何单次生成结果都不得仅因“看起来用户喜欢”而自动登记为长期模板。

## 三、模板选择优先级

模板和写作习惯的解析遵循既有个性化优先级，并增加“模板资产”解释：

```text
Hard Guardrails｜不可覆盖硬规则
        ↓
Matter Override｜当前事项/案件/客户明确要求与事项模板
        ↓
User Personalization｜用户长期习惯与用户模板
        ↓
Version Defaults｜爽律当前版本默认模板/默认样式
```

其中，用户在当前任务中明确说“就用这份模板”“这次不要用我以前的模板”等，应写入当前 TaskProfile / Matter Override，仅影响该任务或用户指定范围，不自动改变长期 User Personalization。

**禁止行为：**

- 新版本因为增加了系统模板，就把用户已有模板替换掉；
- 找不到用户模板时，静默改用系统模板并声称“按你的模板完成”；
- 用户只要求参考某个模板，却把模板中与本案无关的事实、主体、条款或表述复制进新文书；
- 把模板格式一致性置于事实准确性、法律核验和专业判断之上。

如果用户模板与 Hard Guardrails 冲突，只阻止冲突部分生效，并向用户说明；模板文件本身继续保留，不得在升级时删除。

## 四、TemplateAsset｜模板资产

每项长期模板至少记录：

- `asset_id`：稳定标识；
- `name`：用户可识别名称；
- `scope`：`USER / MATTER / CLIENT_OR_PROJECT`；
- `scope_ref`：事项、客户或项目标识（如适用）；
- `document_types`：适用文种；
- `file_path`：用户空间内文件位置；
- `format`：DOCX / MD / TXT / HTML / OTHER；
- `source_type`：USER_PROVIDED / USER_CONFIRMED / MIGRATED_LEGACY；
- `application_mode`：STRICT_STRUCTURE / GUIDED_STRUCTURE / STYLE_REFERENCE；
- `status`：ACTIVE / DISABLED / REVIEW_REQUIRED；
- 可选 Hash、版本和说明。

`STRICT_STRUCTURE` 只表示优先保持结构，不意味着可以违反现行法律、程序要求或事实状态纪律。正式文书在使用旧模板前仍应检查其文种要求、法律依据和格式要求是否仍适用。

## 五、从“生成文件”到“完成任务”

当用户要求“整套材料”“全部立案材料”“配套文书”“一整套合同文件”等，或同一事项显然需要两个以上共享事实基础的交付物时，应考虑建立 `DeliverableBundle`。是否属于法律或程序上“必需”的材料，不得仅凭模型常识猜测。

每个拟交付物必须标记其需求来源：

- `USER_REQUIRED`：用户明确要求；
- `VERIFIED_REQUIRED`：已通过现行规则、官方要求或可靠来源核验为本任务必需；
- `RECOMMENDED`：基于专业工作流建议，但并非已核验强制材料；
- `OPTIONAL`：可选；
- `UNKNOWN_NEEDS_CHECK`：暂不能确认是否需要。

如果任务涉及法院、仲裁机构、行政机关或其他机构的正式提交，成套清单中“哪些材料必须提交”本身属于需要核验的事实/规则，不能把通用经验清单冒充当地当前要求。

## 六、SharedMatterFields｜共享事项字段

多份交付物反复使用的基础信息应建立共享字段，而不是在每份文件里重新生成。典型字段包括主体名称、身份信息、地址、合同日期、金额、程序阶段、案号、诉讼请求、代理人和律所信息等。

共享字段不是“真相数据库”。每个字段仍应记录事实状态和上游依据：

```text
field_id
key / label
value
fact_status
fact_id / source_refs / locator_refs
last_updated_at
```

`ALLEGED / DISPUTED / INFERRED / UNKNOWN` 不得因为被多个文书复用而自动变成 `VERIFIED`。

## 七、变更联动与回写

共享字段发生变化时，应生成 `ChangePropagationEvent｜变更传播事件`，识别受影响交付物。不同变化采用不同处理强度：

1. **机械一致性变化**：如已核验主体名称更正、统一地址格式，可在保持来源的前提下批量更新，并再次校验；
2. **实质事实变化**：如合同日期、交易金额、履行节点改变，应同步检查相关事实、证据、请求、论证和交付物，不能只做字符串替换；
3. **法律或策略变化**：如请求路径、辩护策略、法律评价变化，必须重新进入相应分析/人工决定节点，不得自动批量改写结论。

最终交付前，所有 `REQUIRED` 交付物不得处于 `STALE`；所有会影响最终内容的 `PENDING / REVIEW_REQUIRED` 传播事件应当关闭或明确阻断交付。

## 八、模板与成套交付的质量门

正式任务适用时增加：

- `GATE-TEMPLATE-RESOLUTION`：用户明确指定或已有适用模板时，必须记录使用了哪个模板、为何适用；缺失时应说明，不得静默换成系统模板；
- `GATE-USER-ASSET-PRESERVE`：不得记录任何“静默覆盖用户模板”的行为；升级或导入冲突默认保留现有用户资产；
- `GATE-BUNDLE`：需要成套交付时必须建立 Bundle，并保证用户明确要求/已核验必需的交付物已完成；
- `GATE-BUNDLE-CONSISTENCY`：共享字段变更后不得存在仍需更新的正式交付物或未关闭的重大传播事件。

这些门只检查任务完成度和一致性，不自动判断实体法律结论是否正确。

## 九、升级与迁移

爽律升级 Core 时不进入、不覆盖“爽律用户空间”。用户模板和个性化设置默认原地保留。需要跨设备/跨环境迁移时，使用“导出个性化包 → 新环境导入”的方式；导入发生同名模板冲突时默认 `PRESERVE_CURRENT`，只有用户明确选择后才能采用传入版本覆盖或替换。

旧版本曾直接改 Core 形成模板时，应先识别为 `legacy customization candidate`，再迁入 `custom-templates/`，不能为了保留模板而把整个旧 Core 文件覆盖回新版。

## 十、边界

本规范不要求爽律 Skill 自建长期案件数据库，也不假设所有 Agent 都能持久化二进制模板。平台不支持持久文件时，应明确提示用户导出模板资产包或保存在其自己的项目/云盘中；不得假装已经长期保存。
