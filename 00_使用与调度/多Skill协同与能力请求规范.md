# 多 Skill 协同与能力请求规范

## 一、定位

v0.43 的 Agent Native 不等于把所有工具都塞进爽律。爽律负责律师专业工作的任务理解、事实/证据/法律分析、策略与质量控制；OCR、文件解析、Web、专业数据库、Office、图形渲染、代码等由当前 Agent 的可用工具或其他 Skill 实现。

## 二、统一协同对象

需要外部/其他 Skill 能力时，优先形成：

1. `CapabilityRequirement`：需要什么能力、为什么需要、最低可信度、是否必须保留来源定位；
2. `SkillCollaborationRequest`：需要当前 Agent 找到何种能力、输入边界、期望返回什么、失败时如何降级。

爽律不硬编码“必须调用某某数据库 Skill / OCR Skill / Office Skill”。当前 Agent 可以用任何满足能力契约的实现。

## 三、典型链路

```text
用户任务
→ 爽律自动激活
→ 法律主技能路由
→ 发现输入/检索/交付能力缺口
→ CapabilityRequirement / SkillCollaborationRequest
→ 当前 Agent 选择可用工具或其他 Skill
→ 返回结构化结果 + 来源/限制
→ 爽律继续法律分析
→ 质量门
→ 正式交付
```

例如扫描卷宗任务可以由文件/OCR能力完成文本读取，爽律只接收可追溯的抽取结果并继续证据与法律分析；要求 DOCX 时由可用 Office 能力生成文件，但爽律继续控制文书内容、结构、引用和用户模板。

## 四、协同边界

- 其他 Skill/工具的输出不自动等于已核验事实或现行法；
- 专业数据库摘要不自动等于裁判原文；
- OCR 抽取不自动等于人工核对；
- Office 工具负责“做出文件”，不替爽律决定法律内容；
- 敏感材料外发继续受外部处理风险门控；
- 用户已有模板和个性化优先级不因其他 Skill 介入而改变。

## 五、主动建议

Agent 可以发现当前任务的自然下一步，例如起诉材料可能同时涉及证据目录或保全，但必须遵守：

- 直接服务于当前目标；
- 不把“可能有用”扩展成无限推荐；
- 默认一轮至多一个高价值建议；
- 不把建议冒充法定必需项；
- 重大权利处分和核心策略仍停在人工决定节点。
## 六、协同失败不阻断旧路径

多 Skill 协同属于增强层。`multi_skill_collaboration` 关闭或其他 Skill 不可用时，应先检查 v0.42 已有能力适配、等价工具或明示降级路径。能够按旧能力完成的，不得因为协同增强失败而终止整个法律任务。主动建议亦同：生成失败时直接跳过建议，主任务继续。
