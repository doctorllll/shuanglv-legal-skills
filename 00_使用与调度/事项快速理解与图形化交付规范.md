# 事项快速理解与图形化交付规范

## 一、目的

当用户收到一份合同、一组案件材料、尽调资料或其他复杂法律材料时，第一需求往往不是立即阅读完整法律分析，而是先快速回答：**这是什么、谁参与、事情怎么运作、关键金额和时间是什么、目前处于什么状态、最值得关注什么。**

爽律 Skill 对此建立“事项快速理解层”。它位于详细分析之前，来源于事项工作模型，但面向人类阅读，不替代后续事实、法律、证据和策略分析。

## 二、默认交付：事项快速理解包

收到实质性材料并完成必要审阅后，复杂或正式任务原则上先形成：

1. **一句话事项说明**：谁与谁，因何事项，形成何种法律/交易/争议关系；
2. **事项核心概要**：主体、标的/行为、金额、期限、关键节点、程序/履行状态；
3. **核心示意图**：主体关系、交易结构、资金流、时间线、履行流程、证据关系、问题树或方案树中最有助于理解的一项或数项；
4. **3—7 个核心关注点**：只列概要级问题，不复制详细报告；
5. **重大未知与待核验事项**：防止摘要把不确定内容写成确定事实；
6. **详细成果导航**：告诉用户进一步阅读哪份报告、修订稿、矩阵或证据分析。

对于合同、刑事、民商事、尽调等复杂或正式材料任务，只要存在主体关系、时间过程、交易/履行、资金、证据、问题结构中的任一可图形化关系，原则上至少提供一项核心示意图。简单单页材料或用户只问一个局部问题时可以缩减；确无可图形化关系时，不为了形式制造没有信息价值的图。

## 三、事项核心概要不是“长摘要”

概要应优先提取具有法律和业务意义的要素，而不是按原文顺序压缩全文。

### 合同/交易

至少按需说明：
- 当事人及角色；
- 交易目的和业务模式；
- 标的、对价、金额及支付结构；
- 交付、验收、结算、质保等关键履行节点；
- 合同期限、生效/终止机制；
- 担保、第三方、审批等关键依赖；
- 当前最需要关注的条款或结构问题。

### 刑事案件

至少按需说明：涉案主体及角色、涉嫌/控告路径、核心事实链、金额、程序阶段、主要证据类型、核心争议、强制措施/财产状态和重大缺口。

### 民商事争议

至少按需说明：原被告/申请人与被申请人、法律关系、请求与主要抗辩、标的额、关键履行过程、当前程序阶段、核心争点、保全/执行状态。

### 尽调/专项调查

至少按需说明：标的、交易目的、主体与控制关系、核心资产/业务、重大合同/债务/诉讼、主要红旗和信息缺口。

## 四、事实状态和溯源

事项概要中的压缩表达仍必须继承上游 FactStatus 和来源定位。不得为了“读起来顺”而把 `ALLEGED / DISPUTED / INFERRED / UNKNOWN` 静默升级为已核验事实。

用户可见层使用自然表达，例如“现有材料显示”“A 主张”“目前可确认”“尚需核验”“初步判断”；内部仍保留事实状态、证据和 `SourceLocator`。

图中的关键关系、日期、金额和节点同样应能回到上游材料。图形是分析结果的视觉入口，不是新的事实来源。

## 五、图形类型

高频法律示意图优先标准化为：

- `ENTITY_RELATIONSHIP`：主体/人物/公司关系；
- `TRANSACTION_STRUCTURE`：交易结构；
- `MONEY_FLOW`：资金流；
- `TIMELINE`：时间线；
- `SWIMLANE_TIMELINE`：多主体泳道时间线；
- `PERFORMANCE_FLOW`：合同履行流程；
- `EVIDENCE_MAP`：待证事实—证据关系；
- `ISSUE_TREE`：问题树；
- `OPTION_TREE`：方案/决策树；
- `ARGUMENT_MAP`：论证关系图。

一张图只回答一个主要问题。复杂事项拆成多张图，不把所有主体、资金、证据和争点强塞进一张“蜘蛛网”。

## 六、模型只需“会描述图”，不要求会生图

爽律 Skill 使用 `DiagramSpec` 作为稳定中间层：模型先输出节点、关系、标签、状态、来源和推荐布局，再由当前运行环境选择渲染方式。

```text
事项工作模型
→ DiagramSpec
→ 可用渲染能力
→ 用户可见图形
```

纯文本模型仍可完整生成 `DiagramSpec`，因此图形能力不绑定特定大模型。

## 七、用户最终格式优先级

最终面向普通用户的图形交付，按通用性优先：

1. **PNG**：默认优先。手机、微信、浏览器、Word、PDF 均易查看；
2. **自包含响应式 HTML**：无法直接输出 PNG，但能创建文本文件时的通用保底。HTML 内嵌 SVG/CSS，不依赖外部网络；可选提供本地“导出 PNG”按钮；
3. **PDF/DOCX 中嵌入 PNG 或矢量图**：作为正式报告的一部分；
4. **Mermaid / Graphviz DOT / PlantUML 等图源**：作为可渲染中间产物或开发/协作附件，不作为普通用户唯一成果；
5. **真正只能聊天、不能创建文件也不能渲染**：输出可渲染图源，并同时提供最简 Unicode 示意；必须说明未实际生成图片文件。

SVG 可作为 HTML 内嵌或中间渲染格式，但不作为普通用户默认单独交付文件。

## 八、纯文本模型的 HTML 保底规则

只要模型能创建文本文件，就可以生成单文件 HTML：

```text
HTML
├─ 内嵌 CSS：响应式布局
├─ 内嵌 SVG：节点、连线、箭头、图例
├─ 无外部字体/脚本依赖
└─ 可选本地 JavaScript：将 SVG 绘制到 Canvas 并导出 PNG
```

敏感材料不得为了渲染图形默认上传第三方在线图形服务。确需外部渲染时，仍执行外部处理风险门控和明确授权。

## 九、移动端优先

- 不依赖固定聊天窗口宽度；
- 不把超宽 Markdown 表格或 ASCII 字符图作为正式示意图；
- 手机端优先纵向/分区布局；
- 节点文字保持简短，详细内容放在图下说明；
- 图形过密时拆图；
- PNG 输出应保证放大后仍可辨识关键文字。

## 十、事实状态的视觉表达

如图中需要区分事实状态，推荐：
- 实线：已核验或有可靠材料直接支持；
- 虚线：当事人主张、存在争议或尚待核验；
- 点线：分析推断；
- 图例必须明确含义。

不得仅依赖颜色传递关键法律含义，避免黑白打印或无障碍场景信息丢失。

## 十一、与其他交付物的顺序

复杂材料任务的阅读顺序原则上为：

```text
01 事项快速理解包
02 核心示意图 / 时间线
03 详细专业分析
04 主交付物（合同修订稿、法律文书、意见书等）
05 矩阵、研究、证据表、来源附件
```

目标是：**先让用户看懂，再让用户看深。**
