READ THIS FIRST

先把关系说清楚：用户把任务交给 Agent

爽律skill在整个工作链条中的位置很明确：它是一套面向中国律师实务的 Agent Skills 工作流系统，也是供 Agent 调用的律师专业方法与质量控制层。真正接收用户任务、读取材料、调用工具、生成文件和与用户交互的主体始终是 Agent。

一句话理解
用户提出任务 → Agent识别任务 → Agent按需调用爽律skill中的法律工作方法 → Agent结合实际可用工具执行 → 形成专业结果 → 涉及重大选择和对外行动时由律师/用户决定。

因此，本手册后文统一采用“Agent在爽律skill规则指引下完成某项法律工作”的表述。爽律skill本身不被拟人化，也不被描述成独立办案主体。

QUICK USE

怎么使用：任务仍然交给 Agent

爽律skill不改变你和 Agent 的基本交互方式。你仍然直接告诉 Agent 要做什么；当当前宿主支持 Agent Skills 自动发现时，Agent可以根据法律任务的语义判断是否调用爽律skill。若宿主不支持自动发现，也可以显式要求 Agent 使用爽律skill。

为了让结果更稳定，尤其是复杂法律任务，建议尽量把下面六件事说清楚：

要素用户需要说明什么
角色代表哪一方，或者以什么身份处理当前事项。
目标本轮真正要解决什么问题、取得什么结果。
材料已经提供哪些文件或事实，是否存在缺件、版本差异或未审阅材料。
范围只改格式、做初步分析、完整研究，还是需要形成正式成果。
交付物需要清单、分析、修改稿、研究报告、表格、图形、正式文书或其他成果。
限制期限、篇幅、模板、保密要求、不得外发、不得修改原件或其他明确边界。
一个通用例子
“我们代表甲方。请审查并修改这份合同，重点看付款、验收、知识产权和解除；本轮不做税务分析；不得把文件发送给第三方服务；最后给我清洁稿和修改说明。”

调用方式取决于当前 Agent / 宿主

方式用户体验
AUTO当前宿主支持自动发现时，符合任务语义的法律工作可以自动调用爽律skill。
CONFIRM当是否需要调用处于边界状态时，先确认再进入爽律skill的方法。
MANUAL仅在用户明确要求 Agent 调用爽律skill时使用。

无论采用哪种方式，用户本轮明确的任务要求优先。文件名称、材料数量或材料中偶然出现的法律术语，都不应自动改变任务范围。

IMPORTANT NOTICE

重要风险提示

风险事项使用时应注意什么
敏感材料客户材料、案件材料、个人信息、商业秘密等应根据事项性质先判断是否需要脱敏，并遵循最小必要原则。
外部工具API Key、连接器、数据库或云端工具“可以用”，不等于已经取得把当前材料发送给第三方的授权。
律师复核爽律skill用于约束和增强 Agent 的法律工作方法，不能替代律师对重要结论和正式成果的最终专业复核。
正式法律意见Agent生成的分析、草稿、清单和研究结果不当然构成正式法律意见；是否可以正式对外使用取决于材料、核验、律师复核和签发程序。
现行法涉及正式法律判断时，应根据任务需要实际核验法律、司法解释、地方规则、时间效力和适用范围；未核验就不能声称“已核验现行有效”。
法域爽律skill v0.50目前主要面向中国大陆法律实务；涉及其他法域时，需要重新确认适用规则、职业规范和程序前提。
特别提醒
刑事案件处理请注意保密和材料脱敏。 涉及未公开案卷、会见材料、个人信息或其他敏感内容时，更应谨慎判断是否可以进入第三方模型、OCR、云盘或其他外部处理环境。
PAIN POINTS

真实痛点：公开讨论里反复出现的，是这些问题

这部分重新做了公开检索。样本包括 Reddit、微博、知乎等用户讨论，以及律师行业公开指引和司法案例。它用于识别高频体验，不作统计意义上的“民意排名”。

用户真正会遇到的痛点典型表现
1看起来很真，实际可能是假的虚构法条、案例、事实；旧规则被当成现行规则；来源无法回查。
2指令执行漂移用户明确说“只改格式”“别动正文”，Agent仍可能扩展任务、漏做要求或擅自改变内容。
3长任务前后漂移长对话、多文件、多轮修改后，事实、称谓、金额、版本、已确认决定出现不一致，需要用户反复提醒。
4AI味和信息稀释套话、过度分点、重复总结、句式模板化、“不是……而是……”等高频结构，导致文本顺滑但缺少人味与信息密度。
5内部过程污染成品工作提醒、模型自我说明、研究过程、TODO、对抗性审查残留被带进正式文书或对外材料。
6过度迎合用户预设用户已有结论时，模型可能顺着结论补理由，缺少真正的反证、反例、竞争解释和证伪。
7完成状态与真实执行不一致Agent可能声称“已读取”“已更新”“已生成”，实际工具没有执行、文件没有生成，或只读了部分材料。
8敏感材料与授权边界模糊能够调用云端工具、数据库或API，不等于当前案件材料已经取得外发授权。
为什么这组痛点更重要
这些问题直接影响律师的时间成本、事实可靠性、法律责任、成品质量和客户秘密。它们也是爽律skill多项规则真正要解决的对象。
DESIGN RESPONSE

爽律skill如何对准这些痛点

痛点爽律skill提供的约束与方法
幻觉 / 过时 / 来源不明事实状态、来源定位、现行法核验、研究充分性
指令漂移 / 擅自扩展先区分“用户要求”和“待处理材料”；只调用完成当前目标所需的方法
长任务漂移复杂事项保留最小专业状态；新材料只使相关结果进入待更新
AI味 / 废话 / 套话写作模块强调读者、目的、自然段、信息密度、模板与用户习惯；正式交付再做成品清理
内部过程污染成品内部分析与对外文本分层；正式交付前检查工作过程残留、未核实假设和内部指令
迎合用户预设竞争解释、反向材料、翻转点、对抗性审查
声称完成但未执行执行真实性：没有真实读取、检索、渲染、修订或文件生成，就不能宣称完成
敏感材料外发外部处理前说明服务商、目的、发送范围并取得针对性授权

这里有一个核心思路：爽律skill不承诺“AI从此不会犯错”。它把关键事实状态、来源、授权、人工决定和成品检查变成明确步骤，让错误更容易被发现、定位和纠正。

SYSTEM MAP

一张图看懂爽律skill：三条线同时运行

纵向看，一个任务从“理解用户要求”一路走到“可交付成果”；横向看，事实、证据、研究、分析、策略、写作、复核是五类业务共同使用的基础能力；边界控制贯穿所有场景。

PART I

纵向运行逻辑

先看一项法律任务如何从用户要求进入专业结果。

1. 入口：先搞清楚用户到底要什么

Agent收到任务后，第一件事是区分四类内容：用户要求执行的动作、需要处理的正文、引用或示例、附件和来源材料。这样做可以避免“附件里写着某句话，就被当成新的任务指令”。

对律师最有价值的地方在于“目标优先”。同一份法律意见书，用户可能只要求统一格式，也可能要求重新研究实体问题。文件名称相同，任务完全不同。Agent应以本次明确目标决定工作深度。

例：只调格式
用户说“只统一字体、标题、页码，不改正文”，Agent应进入格式处理和语义保真检查；不能因为文件中出现“案例”“法律依据”等词，就自行启动新的法律研究。
例：完整争议分析
用户要求“完整审阅一组商事争议材料，梳理事实与证据、研究法律问题、形成诉讼策略和代理意见”，Agent才会同时使用事实、证据、研究、法律分析、策略、写作、复核以及民商事争议方法。

2. 选择“够用”的专业工作，不追求形式上的全流程

爽律skill v0.50强调“完成当前任务所需的最小专业工作集合”。它解决两个相反问题：一边是AI容易偷懒，另一边是AI为了显得完整而制造大量无关步骤。

Agent会先加深已经被触发的工作。例如一个证据问题已经明确，就先把该证据问题做深；只有出现新的、会改变结论的信号时，才横向扩展到法律研究、策略或其他业务模块。

  • 简单改写：保持法律含义，重点处理表达与语义保真。
  • 单点法律问题：事实足够时，重点处理现行法、法律分析和结论边界。
  • 复杂事项：逐步进入结构化材料、证据、研究、竞争解释、策略和正式交付。
  • 达到当前交付所需的充分程度后停止，避免为了“流程齐全”继续堆内容。
用户感受到的变化
同一个Agent面对“一句话润色”和“数十份复杂争议材料的综合分析”时，工作方式应明显不同。爽律skill把这种差异写成了稳定规则。

3. 纵向主流程：允许回头，而非一路向前

法律工作经常需要回写。新证据可能改变事实判断；新的现行法可能改变法律评价；对方最强观点可能迫使律师调整策略。爽律skill把这种“前后迭代”保留下来，因此纵向流程是一条可以回头修正的链。

PART II

八项通用能力

这些能力横跨刑事、民商事、合同、尽调和法律顾问，是爽律skill的共同方法底座。

SHARED CAPABILITY · FACTS

1. 事实与结构化审阅

Agent面对大量材料时，先建立“可核对的事实底座”。重点不是长摘要，而是来源、审阅状态、事实状态、时间线、主体关系、矛盾和缺口。

Agent会怎样做

  • 先设定本次真正要回答的审阅问题
  • 收到、部分审阅、完整审阅、不可读等状态分开记录
  • 重要事实保留页码、段落、单元格或时间戳
  • 把陈述、推断、争议和已核验事实分开
  • 多文件时做时间、主体、金额、版本与陈述交叉比较
用户最终能感知到什么
用户得到的通常是：材料台账、事实时间线、关系图、矛盾清单、待核问题，以及后续证据/法律分析可以直接复用的事实记录。
SHARED CAPABILITY · EVIDENCE

2. 证据与证明分析

Agent把“材料里有什么”进一步推进到“它究竟能证明什么”。证据分析围绕待证命题组织，同时检查来源独立性、可靠性、合法性、矛盾和缺失。

Agent会怎样做

  • 先定义需要证明的命题
  • 同时列出支持和反向证据
  • 多份材料若来自同一原始来源，不机械当成多份独立印证
  • 识别按常理应当出现但尚未出现的材料
  • 给出当前证明充分性和剩余不确定性
用户最终能感知到什么
它解决了“证据很多就等于证明充分”的常见误判，也避免把文件数量当成证据强度。
SHARED CAPABILITY · RESEARCH

3. 法律研究与类案

Agent在需要检索时，先界定问题、法域、时间，再寻找并评价来源。研究关注来源角色、现行有效性、案例可比事实、反向材料和检索充分性。

Agent会怎样做

  • 规范、案例、官方解释、实践信号、专业分析各自承担不同作用
  • 现行法必须实际核验后才能标记为“已核验”
  • 类案比较决定性事实和裁判理由，不只看案由/罪名
  • 主动寻找反向、边界和例外材料
  • 新一轮检索已经很难改变结论时才考虑停止
用户最终能感知到什么
输出可以是法规沿革、类案矩阵、研究备忘录、研究包或供正式法律意见使用的研究底稿。
SHARED CAPABILITY · REASONING

4. 法律分析与论证

Agent把事实、证据和法律连接成可复核的法律判断。它强调问题构造、规则适用、竞争解释、结论边界，并允许因为新事实或新规则回到前面重做。

Agent会怎样做

  • 从客户目标和事实中主动发现真正法律问题
  • 规则要落到有支持的事实，不能从法条名称直接跳结论
  • 重要结论至少接受一个有真实压力的竞争解释
  • 关注“哪个事实/规则变化会让结论翻转”
  • 结论确定性与事实、证据、来源支持程度保持一致
用户最终能感知到什么
这部分形成的问题树、要件分析、规则—事实适用、竞争解释和分层结论，随后由策略和写作模块使用。
SHARED CAPABILITY · STRATEGY

5. 策略与选项

法律上可行的方案往往不止一条。Agent在爽律skill方法下比较法律可行性、证据成熟度、时点、成本、可逆性、对方反应和执行效果，再把重大选择留给人。

Agent会怎样做

  • 形成可行选项，而非只给一个“建议”
  • 比较优劣、依赖条件和风险
  • 区分专业推荐与最终决定
  • 重要或不可逆选择明确停在律师/客户节点
  • 决定作出后，回写研究范围、证据计划和文书策略
用户最终能感知到什么
用户得到的是“可决策的选项集”，而不是一长段抽象风险提示。
SHARED CAPABILITY · COMPOSITION

6. 法律写作与交付内容

Agent把上游事实、研究和分析转成真正适合当前读者的法律文本。核心是作者、读者、目的、文种、事实完整性、论证结构、语言自然度、引用和版本。

Agent会怎样做

  • 正式文书从结构化分析结果出发，不直接把原始材料拼成文章
  • 写给法院、检察机关、客户、交易对手的表达方式分别处理
  • 避免一句一段、机械小标题、套话、无意义加粗和重复总结
  • 用户已有模板和合法写作习惯优先保留
  • 语义定稿与DOCX/PDF等物理渲染分开
用户最终能感知到什么
这也是解决“AI味”和“成品不像律师写的”问题的主要模块。
一个很实际的要求
正式文件里不应残留模型自我说明、研究过程、TODO、对抗性审查用语、内部指令或“我已经帮你……”这类工作过程文本。
SHARED CAPABILITY · REVIEW

7. 复核、对抗与溯源

重要结论形成后，Agent再用第二视角攻击初步方案，寻找最强反方路径、翻转点和真正缺陷；同时保证重要结论能回到事实、证据、法律和来源。

Agent会怎样做

  • 先冻结当前结论，明确它依赖什么
  • 构造最强可信反方，而非稻草人
  • 发现反向材料后必须回写原结论
  • 区分真实弱点和泛泛谨慎
  • 正式对外文本只带入适合当前受众且已核实的内容
用户最终能感知到什么
它解决“AI顺着用户说”和“表面有引用、实际上无法追溯”的两类可靠性问题。
SHARED CAPABILITY · VISUALIZATION

8. 法律可视化

当时间、主体、资金、履行、证据、要件或论证结构仅靠文字难以低成本理解时，Agent可以把已经形成的事实、证据和分析结构转换为图形。可视化不是另建一套事实，也不是为了“好看”而删减不利信息。

Agent会怎样做

  • 先判断图形是否真的比文字或表格更清楚；简单问题不强行画图
  • 根据法律结构选择时间线、关系图、交易结构、资金流、履行流程、证据图、要件—证据图、争点树、论证图或方案比较图
  • 节点、金额、日期、证据状态和关系方向沿用既有事实/证据/论证对象，不重新编造
  • 默认先保证可靠静态版；搜索、筛选、钻取、切换视角确有价值且当前宿主 支持时，再提供交互版
  • 图形同样接受来源、事实状态、反向信息和正式交付检查，不能把推断画成已核验事实，也不能把同源证据画成独立印证
用户最终能感知到什么
复杂案件和交易结构可以更快“看懂”：时间先后、主体关系、资金去向、证据覆盖与缺口、争点层级和论证攻防会被显式呈现，同时仍能回到原始来源复核。
一个底线
隐藏 ≠ 删除；筛选 ≠ 否认；聚焦 ≠ 证明。 图形可以帮助表达和比较，但不能改变法律事实状态、证明强度或论证边界。
PART III

五类法律业务工作流

通用能力进入具体业务后，会按律师的角色、阶段、交易和程序问题形成不同工作路径。

DOMAIN WORKFLOW

1. 刑事案件办理

公开使用提醒
刑事案件处理请注意保密和材料脱敏。 本节用于解释爽律skill的刑事业务方法，不意味着建议把真实案卷、会见材料或其他敏感内容上传到未经评估的第三方服务。

刑事案件首先看律师角色、程序阶段和当前任务。辩护、被害人代理、控告报案对应不同证明模型；会见、阅卷、罪名、强制措施、认罪认罚、庭审也不能混成一条固定模板。

这条业务线最重要的方法

  • 角色×阶段×任务决定路线
  • 会见陈述先作为待核信息，与卷宗交叉验证
  • 阅卷先理解控方证明体系，再找矛盾、同源信息、缺失证据和替代解释
  • 罪名分析从可支持的事实模型出发，建立要件矩阵
  • 发现控方缺口后，是否立即披露属于策略问题，需要考虑阶段目标和补强空间
典型交付
核心成果：控方证明地图、事实时间线、证据矩阵、矛盾矩阵、罪名要件矩阵、会见提纲、阶段策略、辩护/控告/代理文书等。
DOMAIN WORKFLOW

2. 民商事争议解决

民商事工作围绕客户真正要实现的法律效果组织。Agent需要同时处理请求/抗辩、争点、证明责任、程序、保全、和解和执行，而不能只围绕“写起诉状”展开。

这条业务线最重要的方法

  • 先问客户真正想拿到什么结果以及执行是否现实
  • 原告建立主位/备位请求权基础；被告区分否认、抗辩和反抗辩
  • 争点来自“要件×双方相反主张”，背景差异不自动升级为争点
  • 证据围绕待证命题组织并配置证明责任
  • 管辖、时效、保全、执行等程序问题尽量前置
典型交付
核心成果：请求/抗辩矩阵、争点矩阵、证明责任与证据矩阵、程序问题清单、诉讼策略、庭前/庭审材料、和解与执行方案。
DOMAIN WORKFLOW

3. 合同与交易工作

合同工作先理解交易，再处理文字。代表哪一方、交易怎么履行、哪里可能失败、风险如何分配、以后如何证明履约，会决定条款应该如何起草和修改。

这条业务线最重要的方法

  • 先确认代表方、客户目标、谈判地位和工作深度
  • 建立交易结构、文件体系和履行流程
  • 同时模拟对方违约、我方违约、第三方/审批失败等场景
  • 条款按功能审查：义务、条件、程序、救济、风险分配
  • 用户要求修改合同时，成熟建议应实际落到合同文本，报告只做辅助
典型交付
核心成果：交易结构图、履行与义务地图、风险场景、条款审查意见、实际修订稿、谈判首选/备选文本、签署和履行交接清单。
DOMAIN WORKFLOW

4. 尽职调查与专项调查

尽调以交易或决策为目标，资料清单只是手段。Agent需要界定范围、记录资料质量、进行多源核验、识别真正影响交易的红旗，并把风险传递给合同和后续决策。

这条业务线最重要的方法

  • 调查目的决定范围、排除项和优先级
  • 动态资料清单说明“为什么需要这份资料”
  • 收到文件与核验事实分开
  • 重要事实通过公开信息、访谈、现场或第三方进行交叉
  • 红旗必须说明事实、法律意义、交易影响、缺口和下一步措施
典型交付
核心成果：尽调范围、动态资料清单、材料台账、事实核验表、红旗事项、信息缺口、补件清单、交易影响分析和尽调报告。
DOMAIN WORKFLOW

5. 法律顾问与专项分析

法律顾问场景的重点是把客户表面问题改造成真正的决策问题，然后区分事实基础、法律结论、律师建议、客户决定和行动计划。

这条业务线最重要的方法

  • 先识别客户真正目标和本次决策场景
  • 已知、陈述、争议、未知和假设分开
  • 问题树连接事实、法律研究和法律分析
  • 风险与机会一起看，寻找合法替代结构和补救路径
  • 多方案用同一维度比较，最后形成行动计划
典型交付
核心成果：重新定义的问题、事实基础表、问题树、研究结果、风险/机会图、方案比较、律师建议、客户决策事项和行动计划。
PART IV

为什么它更值得信赖

可信来自可检查的工作机制、明确边界和真实状态，不来自“AI一定正确”的承诺。

1. 六条底线：先保证“说真话”

底线对用户意味着什么
状态真实收到材料、已打开、已审阅、部分审阅、无法读取必须区分。
执行真实没有真实读取、检索、渲染、原生修订或工具执行，就不宣称已完成。
不编造事实、证据、法条、案例、来源、文件状态和执行结果都不能补全。
结论不过度结论确定性不能高于事实、证据、法律和来源的支持程度。
专业判断与行动授权分开完成法律分析或形成FINAL稿，不自动等于可以发送、提交、签署。
重大选择由人作出认罪、放弃权利、上诉、和解、重大交易立场等只能分析和建议。
这里的“可信”含义
爽律skill把“哪里有不确定性、哪里没有真实执行、哪里需要人工决定”暴露给用户。它追求可复核，而非用流畅语言掩盖缺口。

2. 七道风险边界（上）：法律、数据、人

边界它在防什么
现行法核验结论依赖法律是否现行有效时，Agent必须实际查证来源、版本、生效时间和法域；未核验只能明确标为初步/未核验。
敏感材料外部处理把案件材料送到第三方模型/API前，要说明服务商、目的、数据范围和潜在留存/跨境风险，并取得针对性授权。
重大人工决定涉及认罪、和解、上诉、放弃权利、重大交易立场等，Agent提供选项和分析，最终选择停在人。
正式法律交付起诉状、辩护意见、正式法律意见、合同终稿等，需要额外检查内容支持、来源、未解决不确定性和正式文件清洁度。

这些边界和业务方法是交叉关系。例如“材料分析已经完成”本身不会自动取得把客户文件发送到第三方OCR或模型的权限；“法律顾问分析完成”也不会自动取得发邮件或签署文件的权限。

3. 七道风险边界（下）：行动、原件、用户资产

边界用户能得到的保护
对外行动授权发送、提交、签署、删除、修改权威数据等有外部效果的动作，需要针对具体动作、对象和版本的授权。
原始资料保护原始证据和法律来源默认保持不变，优先在副本或派生文件上编辑；必须修改原件时需要明确授权和可审计能力。
用户模板/资产迁移升级版本时不静默覆盖用户已有模板、House Style和长期法律工作偏好；路径变化也不能被当作资产不存在。
一个容易被忽略的区别
“我建议你接受和解”属于专业建议；“我替你点击接受并发送给对方”属于外部行动。爽律skill把两者拆开处理。
PART V

复杂事项、工具协作与个性化

长期案件需要连续性；外部工具要诚实；用户习惯应当被继承。

1. 复杂事项：让前后工作接得上

复杂事项可以保存来源索引、已经形成的专业结果、人工决定、待解决问题和续接摘要。恢复时只取当前子任务真正需要的信息，减少长对话把无关内容重新塞进上下文。

新证据或新法律规则进入后，系统沿着明确依赖关系找到受影响结果。只有这些结果进入待更新，无关结果继续复用。这个设计直接针对“长任务前后漂移”和“每轮都从头做”的痛点。

边界
这种连续性只服务于法律专业工作。它不等同于完整案件数据库、CRM、通用项目管理器，也不会把一次会话的发送授权自动带到下一次会话。

2. 大量同类材料：批处理也要先控制质量

批量处理不是把同一个提示词机械跑几十遍。Agent会先定义本批任务真正要提取、比较或判断的字段，并根据材料差异、错误代价和外部处理成本决定是否需要先做小样本校准。

1
定义批任务。 明确材料范围、字段、输出格式、异常条件和必须保留的来源定位。
2
必要时先试跑。 材料异质、规则复杂或错误代价较高时，先用少量样本验证口径；少量简单材料不会被强制套重流程。
3
批量执行。 统一处理，同时保持每个结果与原文件、页码、Sheet、时间戳等位置的对应关系。
4
异常单列。 冲突、缺件、低置信识别、超出规则范围和高风险项进入异常清单，不用平均值或默认答案掩盖。
5
汇总与复核。 只对真正需要人工判断或会改变结论的项目设置人工闸门。
适合的场景
批量合同条款比对、银行流水/发票/聊天记录结构化、尽调资料核对、类案卡片整理、批量律师函底稿等。批处理的目标是减少重复劳动，不是降低每一项结果的可追溯性。

3. 外部工具：爽律skill规定“需要什么”，Agent负责“用什么执行”

OCR、网页检索、法律数据库、电子表格、DOCX/PDF生成、原生修订、多模态识别等，都取决于当前Agent或宿主是否真的具备相应能力。爽律skill负责规定法律任务对这些能力的输入、输出、质量、来源和降级要求。

当工具不可用时

  • 有同等可信替代能力：继续执行。
  • 只能用较弱方案：可以降级完成，但要告诉用户影响在哪里。
  • 缺失能力会破坏核心正确性：明确阻断，不假装完成。
典型例子
用户要求“Word原生修订”。当前Agent真实支持Track Changes时可以执行；不支持时只能明确降级为差异稿+清洁稿，或在用户坚持原生修订时停止。红字不可以冒充原生修订。

4. 专门 Skill 与跨工具协作：谁更专业，谁负责主导

当系统中存在更窄、更完整的专门Skill时，Agent可以让该专门Skill在其范围内主导；遇到跨问题综合时，再由爽律skill提供通用法律方法和整合。这样可以避免所有Skill一起加载、重复做同一件事。

跨Skill、跨工具传递材料时，遵循“最少必要披露”：只传递完成子任务所需的事实、结果和材料，不把其他案件、无关用户信息或全部上下文一起带过去。

场景合理分工
窄域专门Skill完整覆盖专门Skill主导当前子任务
没有更窄Skill完整覆盖Agent按爽律skill通用方法处理
多个专业结果需要综合爽律skill提供跨问题法律整合
OCR/数据库/文档工具只提供能力，不取得法律方法主导权

5. 用户偏好与模板：系统升级，不应把你的写作习惯洗掉

爽律skill允许保存法律工作相关偏好，例如篇幅、标题习惯、结论前置、研究深度、格式、House Style和用户模板。它同时设定优先级，确保个性化不会覆盖事实真实性、现行法核验、来源追溯、敏感材料授权和重大人工决定。

优先级来源适用顺序
硬性专业与安全边界最高
本次任务明确要求其次
用户长期法律工作偏好/模板再次
版本默认最后
对律师真正重要的一点
旧模板可以提供结构、样式和表达参照；旧案件的事实、主体、金额、结论和旧法律版本不能被复制进新事项。

激活方式也属于可配置偏好：支持自动识别、边界任务先确认、只在明确调用时使用。当前用户在本轮任务里的明确要求始终优先。

6. 专业成果与实体文件：内容完成，不等于文件已经生成

爽律skill把“法律专业内容已经形成”和“DOCX / PDF / 修订稿 / 图形等实体文件已经真实生成”分开。这样可以避免最常见的假完成：文字里说“已生成”，但文件实际上不存在、打不开、版式错误或没有真正完成修订。

  • 专业内容先明确文种、受众、立场、事实/法律来源、关键论证和交付边界
  • 实体文件由当前 Agent / 宿主 的真实文档能力负责生成和渲染
  • 声称“已生成 DOCX / PDF / 修订稿 / HTML”前，文件必须真实存在并能正常打开
  • 正式文件还要检查字体、换行、表格、分页、编号、图形溢出以及多份文件之间的主体、日期、金额和附件编号一致性
  • 发送、提交、签署仍是另一个动作，不因文件完成而自动取得授权
用户最终能感知到什么
“写完了”和“交付件真的可用”不再混在一起。对于正式成果，Agent需要把语义正确、文件真实、视觉可用和对外授权分别说清楚。
PART VI

七个场景，理解它如何实际运行

把前面的抽象方法放回律师每天会遇到的任务。

WORKED EXAMPLE

场景一：只改格式的法律意见书

1
用户：只统一字体、标题、页码，不改正文。
2
Agent识别“格式限定”后，不因为正文包含法条、案例或争议事实而扩展研究任务。
3
如果需要生成DOCX/PDF，Agent调用真实文档能力；同时检查格式动作没有改变实体内容。
4
发现正文里有明显法律错误，可以单独提示，不静默改掉。
这个场景体现的运行特点
任务目标决定深度；事实、证据、法律、策略和交付按需要组合；真实工具能力与法律专业方法分开；重大决定和对外行动保留人工边界。
WORKED EXAMPLE

场景二：复杂商事争议材料分析与代理方案

1
Agent先建立材料目录、审阅状态和任务问题，再梳理事实时间线、主体关系和交易/履行关系。
2
证据围绕待证命题组织，检查来源独立性、前后矛盾、关键缺口、应当存在但尚未取得的材料以及替代解释。
3
法律分析从现有材料能够支持的事实模型出发；需要依赖现行法律或类案时，再实际检索并核验。
4
Agent比较起诉、应诉、保全、和解、补证等可能路径；撤诉、和解核心条件、放弃重要请求等重大处分仍停在律师/客户决定节点。
5
需要正式代理意见、起诉/答辩材料或其他对外成果时，再进入写作、反向复核和正式交付检查。
这个场景体现的运行特点
任务目标决定深度；事实、证据、法律、策略和交付按需要组合；真实工具能力与法律专业方法分开；重大决定和对外行动保留人工边界。
WORKED EXAMPLE

场景三：类案检索与法律研究

1
Agent先把问题拆成法域、时间、关键事实和法律命题，再确定需要哪些类型的来源。
2
案例按照决定性事实、裁判理由、支持/反向/边界用途比较，避免“案由相同=类案”。
3
数据库摘要只能作为候选线索；重要结论回到原始来源核验。
4
检索停止依据是信息增益和覆盖，不用案例数量凑“完整”。
这个场景体现的运行特点
任务目标决定深度；事实、证据、法律、策略和交付按需要组合；真实工具能力与法律专业方法分开；重大决定和对外行动保留人工边界。
WORKED EXAMPLE

场景四：合同审查并要求实际修改

1
Agent先确认代表方、交易目标、履行流程和谈判地位，再识别风险场景。
2
条款按照功能和失败场景审查；成熟建议应直接落到修订文本。
3
对高风险条款同时给首选、备选和让步条件，让客户看到真实谈判空间。
4
用户要求Word原生修订时，必须以当前Agent真实能力为准。

任务目标决定深度；事实、证据、法律、策略和交付按需要组合；真实工具能力与法律专业方法分开；重大决定和对外行动保留人工边界。
WORKED EXAMPLE

场景五：长周期事项出现新证据

1
Agent读取已有来源、专业结果、人工决定和待解决问题。
2
新证据只使依赖它的事实、法律分析、策略或文书进入待更新；无关成果继续复用。
3
跨会话恢复时只带入本次子任务需要的信息。
4
过去的发送/签署授权不会因为事项连续性而自动延续。
这个场景体现的运行特点
任务目标决定深度；事实、证据、法律、策略和交付按需要组合；真实工具能力与法律专业方法分开；重大决定和对外行动保留人工边界。
WORKED EXAMPLE

场景六：几十份同类材料需要批量审阅

1
Agent先确定批量任务：例如每份合同都检查付款、验收、知识产权、违约责任和解除，并要求保留条款定位。
2
若合同模板差异较大，先抽取少量样本校准字段和判断口径；同质性高且规则明确时可以直接批量处理。
3
批量结果除常规字段外，单列无法识别、条款冲突、规则外情形和高风险项。
4
最终给总表、异常清单和需要律师复核的重点，不让少量异常污染全部结果，也不为“流程完整”让每份材料都走同样重的审查。
这个场景体现的运行特点
批处理仍然服从“小任务小流程、大任务按需要加深”；效率来自统一口径、异常分流和结果复用，而不是牺牲单项质量。
WORKED EXAMPLE

场景七：把复杂资金流和证据链做成庭审/汇报图

1
Agent先用原始材料建立主体、时间、金额、账户和证据状态，不直接从“画图需求”开始猜结构。
2
判断最适合的图型：资金多跳用资金流，时间与行为交织可用泳道时间线，待证事实与材料对应可用证据图。
3
静态版先确认金额、方向、日期、主体、来源和事实状态；交互版只在搜索、筛选、路径高亮或视角切换确有价值时追加。
4
正式使用前做视觉与语义双重检查：不允许为了简洁隐藏关键反向证据，也不允许把推断、争议或同源材料画成确定事实和独立印证。
这个场景体现的运行特点
可视化是事实、证据和论证的表达层，不是第二套案件数据库。图越重要，来源和状态越要能回查。
PART VII

亮点、边界与使用建议

把“优势”说具体，也把做不到的事情写清楚。

1. 当前版本最值得注意的九个特点

特点对用户的实际价值
任务目标优先文件叫什么、材料有多少，都不直接决定工作深度；本轮真实目标优先。
小任务小流程不强迫简单任务跑完整办案链；高风险任务才逐步加深。
事实—证据—法律可追溯重要结论尽量回到来源位置、事实状态、证据和法律依据。
反向检查进入流程不满足于“支持我方”的材料，主动找反证、反例、翻转点和竞争解释。
内部分析与外部成品隔离工作过程可以充分讨论风险和弱点；对外文件只保留适合受众、已核实且有专业价值的内容。
复杂事项可续接且局部更新不靠一条无限增长的聊天记录维持专业连续性。
外部能力松耦合法律方法不绑定某一家数据库、OCR、Office或模型；工具更换不应改变法律判断方法。
批量任务统一口径、异常分流大量材料可以提高效率，但冲突、缺件、低置信和高风险项不会被批量流程掩盖。
法律可视化与原始语义同源复杂结构可以更直观，但图形不能改变事实状态、金额日期、关系方向、证据独立性和反向信息。

2. 它解决不了什么

  • 无法保证零幻觉。它通过来源、状态、核验和复核降低错误进入正式成果的概率。
  • 无法替代律师承担最终专业责任。重大选择、正式签发和职业判断仍需要律师。
  • 无法凭空获得法律数据库、OCR、Word原生修订或多模态能力。是否能执行取决于当前Agent/宿主。
  • 无法把“知识库里有”自动变成“现行法律有效”或“当前案件事实已核验”。
  • 无法把复杂事项连续性等同于完整案件管理系统。当前只保存法律工作续接所需的最小状态。
  • 当前没有独立的行政诉讼业务模块，也没有独立的企业合规业务模块；法律顾问属于相对轻量的专项分析能力。
合理期待
爽律skill的价值集中在“让Agent按更稳定的律师工作方法办事”。模型能力、工具能力、材料质量和律师复核仍然决定最终上限。

3. 怎样向 Agent 下任务，效果最稳定

用户不需要学习工程术语。把下面六件事交代清楚，通常就能明显减少来回纠错。

要素可以怎样说
角色我们代表谁？律师处于什么位置？
目标最终想解决什么问题或取得什么结果？
材料有哪些文件/事实已经提供？哪些还没有？
范围本轮做到哪里？哪些内容明确不要动？
交付需要报告、合同修订、研究包、表格、图形还是正式文件？
限制期限、保密、不得外发、不得修改原件、指定模板等。
示例
“我们代表甲方。请审查这份合同并直接形成修订稿，重点看付款、验收、知识产权和解除；本轮不要做税务分析；不得把文件发送给第三方服务；最终给我清洁稿+修改说明。”
使用与维护

安装、调用与自动更新

用户不需要理解内部文件结构。把正式包或仓库链接交给具备相应权限的 Agent，说明“安装”或“更新到最新正式版”即可。

1. 第一次安装：把正式包或仓库交给 Agent

如果当前 Agent 支持联网、读取仓库并写入 Skill 目录，可以直接把仓库链接发给它，并说明：

可以直接复制
“帮我安装这个爽律skill，并确认安装完成后可以正常调用。”

Agent 应识别正式运行入口，完成必要文件放置，并核对当前安装版本。若宿主只能读取文件而不能写入安装目录，应明确说明需要用户完成哪一个最小人工步骤，不应声称已经安装。

2. 日常调用：直接说法律任务

在支持自动发现的宿主中，直接提出法律任务即可；需要显式调用时，可以说“调用爽律skill”“用爽律skill处理这个案件/合同/研究任务”。用户不需要记忆内部模块名。

你要做什么可以怎样说
复杂案件分析“调用爽律skill。先把这组材料建立事实、证据和争点，再决定哪些问题需要法律研究，不要直接跳到正式文书。”
合同审改“调用爽律skill。我们代表甲方，先分析履行和风险，再直接形成修改稿和修改说明。”
法律研究“调用爽律skill。核验现行法、地方规则、支持与反向案例，并说明哪些结论仍有不确定性。”
可视化“调用爽律skill。先判断哪些结构值得可视化，再基于已核验的事实、证据和分析生成图形。”

3. 自动更新：把同一个仓库链接再发给 Agent

需要升级时，不必重新研究目录结构。把仓库链接交给具备联网和文件写入权限的 Agent，直接说：

更新指令
“帮我把这个爽律skill更新到最新正式版。”

更新时应保护用户自己的模板、合法工作偏好和事项资料，只替换爽律skill的正式运行层及对应用户文档；更新完成后，应核对版本、必要文件和运行入口是否完整。没有真实完成写入和核对，就不能声称“已经更新”。

4. 更新以后，用户自己的东西不应被洗掉

  • 用户自己的文书模板、格式规范和合法工作偏好应继续保留
  • 正在办理事项的材料、结果和续接信息不应因为升级而被无关覆盖
  • 当前任务的明确要求仍然优先于版本默认
  • 如果新版涉及资产迁移，应先识别影响并保护原始用户资产
判断是否真的更新成功
最基本的判断不是 Agent 说了“已更新”，而是它能够指出当前版本、确认正式运行入口真实存在，并说明用户资产是否保持不变。
