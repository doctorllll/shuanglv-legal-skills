# 工程执行层说明

## 一、定位

工程执行层用于把爽律 Skill 已有的专业工作流变成更稳定、可重复、可检查的执行过程。

它重点负责六件事：

1. **渐进式加载**：根据当前任务只读取真正需要的技能文件；
2. **分析与推理约束**：在业务工作流中加载统一分析闭环和业务专属分析方法；
3. **通用结构化审阅**：多文件、跨来源或需要证据/版本比较时，先建立可追溯的材料工作模型；
4. **跨模块交接与回写**：把法律研究、论证、策略比较、对抗性审查和人工决定连接起来，并检查后续发现是否真正更新了原分析；
5. **动态清单**：根据主技能、律师角色、程序阶段、任务类型和交付要求生成本次检查清单；
6. **质量门控**：正式交付前检查关键步骤是否真实完成，发现阻断事项时停止交付。

工程执行层**不负责作出实体法律结论**，也不把静态法条、案例或罪名知识写入代码作为自动判断依据。

## 二、可选而非强依赖

如果当前 Agent 可以运行本地 Python，可以调用：

`05_工程执行层/工具/爽律 Skill执行器.py`

如果当前 Agent 不能运行 Python，仍然可以直接按照系统规则文件执行：

- 《法律分析与推理规范》；
- 《通用结构化审阅规范》；
- 《渐进式加载规则》；
- 《动态清单规则》；
- 《质量门控规则》。

因此，工程执行层是**执行增强层**，不是爽律 Skill 的单点依赖。

## 三、标准执行路径

```text
用户任务
→ 爽律 Skill入口
→ 形成执行计划
→ 渐进式加载主技能
→ 按触发条件加载辅助技能
→ 生成本次动态清单
→ 必要时建立通用结构化审阅
→ 执行业务工作流 + 分析与推理闭环
→ 需要时发起 ResearchRequest 并接收 ResearchResult
→ 多方案任务形成 OptionRecord / DecisionRecord
→ 重要任务执行对抗性审查
→ 将新研究、审查或人工决定回写上游对象
→ 更新执行状态
→ 质量门控
→ 通过：交付
→ 未通过：修正 / 补充 / 人工升级 / 阻断
```

## 四、三个状态必须区分

### 计划状态
回答“本次准备怎么做、准备加载什么”。

### 执行状态
回答“实际做了什么、哪些步骤已经完成”。

### 交付状态
回答“是否已经满足正式交付条件”。

不得用“计划执行”冒充“已经执行”，也不得因为加载了某项规则就声称该规则已经完成。

## 五、工程层不做的事情

- 不用关键词匹配直接认定法律结论；
- 不生成伪精确胜诉率、定罪概率或风险百分比；
- 不用本地版本号替代现行法官方核验；
- 不把 API Key 视为敏感材料外发授权；
- 不把脚本返回 `PASS` 视为律师已经完成专业复核；
- 不用自动化绕过《人工决策与升级矩阵》。


## 全链路溯源检查

工程执行层可以对结构化溯源包执行引用完整性检查，识别断链 ID、缺少来源定位的已核验法律、没有推断依据的 INFERRED 事实，以及无法回到上游分析的正式交付命题。该检查只验证结构完整性，不判断法律观点本身是否正确。


## 跨模块执行检查

工程执行器提供 `chain-check`，用于检查研究请求/结果、策略选项、人工决定、对抗性审查和回写事件之间是否存在断链或未决节点。它只检查执行结构，不评价实体法律结论。

## 事项工作模型增强

工程层可以对复杂任务记录 TaskProfile、MatterWorkingModel、IssueTree、ReviewQuestionSet、AuthorityMap、CaseMatrix、ArgumentMap、计划确认和行为契约状态。脚本只检查对象是否存在、引用是否断裂和门控状态，不评价实体法律结论是否正确。


## 外部能力适配

工程执行层增加运行能力解析：执行计划可以声明是否需要专业法律信源、用户知识库、OCR、DOCX/PDF 或原生修订模式；`capability-check` 可将任务需求与 `RuntimeCapabilityProfile` 对照，输出已满足、降级和阻断项。

该检查不验证第三方工具服务质量本身，也不代表已经获得敏感材料外发授权；涉及外部处理仍由风险门控单独控制。
