# 法律顾问与专项法律分析——分析与推理方法

专项法律分析的核心不是对客户问题逐句回答，而是把业务目标、事实基础、法律规则和可执行方案连接起来。

## 1. 问题重构

先区分客户表面问题、真正决策目标、约束条件和隐含前提。必要时把一个问题拆成事实问题、法律问题、业务判断和客户决定四类。

## 2. 事实基础

明确已核验事实、客户陈述、假设、争议和未知。对结论高度敏感的事实单独标记，并说明需要什么材料才能确认。

## 3. 法律研究与适用

围绕决策需要定位规则，而不是追求资料数量。将规则适用于不同事实场景，形成条件式结论；重大法律依据必须核验当前有效性。

## 4. 竞争方案

至少比较可行方案、风险、前提、成本、时间、可逆性和失败后果。客户希望得到某个答案时，也必须分析相反结论或不采取行动的后果。

## 5. 策略与行动

建议应转化为下一步动作、责任人/决策人、需要补充的材料、时间点和触发条件。不能停留在“建议加强管理”“建议谨慎处理”等抽象表达。

## 6. 论证表达

正式意见明确区分：事实、法律规则、分析判断、商业/经验判断、客户选择。对不确定问题给出条件、范围和需要进一步确认的事项。


## 溯源要求

本技能的所有重要专业判断同时适用《全链路溯源规范》：事实应回到材料/证据和来源定位；法律规则和案例应回到权威来源及具体位置；核心分析应形成可审计的规则—事实—证据—理由链；正式交付中的重要命题应能够反向关联上游 Finding / Argument / Fact / Rule / Case 等对象。无法完成溯源时，应降低结论强度、披露限制或阻断正式交付。

## 跨模块交接与回写

- 专项问题需要法律、案例、监管或用户知识库核验时，先形成明确的 `ResearchRequest`，研究结果回填原问题和方案比较。
- 多方案建议尽量使用共同维度形成 `OptionRecord`，区分“法律上可行”“专业上推荐”和“客户最终决定”。
- 用户改变业务目标、风险容忍度或关键事实后，应回写受影响的 `IssueRecord / ArgumentRecord / Finding`，并重新检查正式意见。

## TaskProfile 与 IssueTree

专项分析应先把决策者、真实目标、业务约束、时间窗口和完成标准写入 TaskProfile，再通过 IssueTree 区分法律问题、事实问题、证据问题和业务决策问题。方案比较应回到相同目标和约束，避免把纯法律可行性直接当成业务建议。
