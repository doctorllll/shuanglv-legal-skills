# 法律文书质量与格式控制——分析与推理方法

本技能不替业务技能重新做实体分析，但负责检查业务分析是否已经转化为完整、可审查和适合目标文种的论证。

## 1. 论证完整性

对每个重大结论检查：是否有明确问题、适用规则、关键事实、证据或来源、推理连接、结论边界。出现“显然”“不难看出”“综合可知”等跳跃词时，检查是否缺少中间论证。

## 2. 事实与评价分离

文书不得把主张、推断或经验判断写成已核验事实。引用事实时尽量保留来源定位；对外文书的策略性表述不能改变内部事实状态。

## 3. 反方与回应

重要文书检查是否识别对方最强观点、最不利事实、规则例外和结论翻转点。根据文种和策略决定是否全部写入正文，但内部 QA 必须完成。

## 4. 结构服务于问题

标题、段落和顺序应服务于争点和读者决策，不按固定模板机械排列。正式文书的法定/官方结构要求优先于一般写作偏好。

## 5. 语言强度

结论强度必须与事实和法律依据匹配。证据不足、规则有争议或资料不完整时，不通过修辞把不确定问题写成确定结论。

## 6. 交付一致性

修订稿、清洁稿、对比稿、PDF 等不同版本的实体内容应一致；技术工具不能实现原生修订或批注时必须披露能力降级。


## 溯源要求

本技能的所有重要专业判断同时适用《全链路溯源规范》：事实应回到材料/证据和来源定位；法律规则和案例应回到权威来源及具体位置；核心分析应形成可审计的规则—事实—证据—理由链；正式交付中的重要命题应能够反向关联上游 Finding / Argument / Fact / Rule / Case 等对象。无法完成溯源时，应降低结论强度、披露限制或阻断正式交付。

## 跨模块交接与回写

文书阶段原则上消费已经形成的事实、规则、论证和 `DeliverableClaim`，不得为了语言流畅擅自创造新的实体结论。

如果文书 QA 发现：

- 上游事实与正文不一致；
- 引用法律或案例无法支持对应命题；
- 对抗性审查后的修订没有进入最终文本；
- 用户人工决定与当前草稿策略不一致；

应把问题回写到对应上游对象并重新确认，而不是只在文书层静默修正。

## 工作模型与文书映射

复杂正式文书应尽量从 MatterWorkingModel 已确认的 Fact / Rule / Case / Argument / Finding 生成。IssueTree 可用于章节组织，ArgumentMap 可用于检查论证冲突；文书阶段不得为了语言流畅擅自创造新的事实、规则或论证前提。

## 7. 成文决策与说理比例（v0.42 原型）

分析完成后先回答“最终读者真正需要解决什么”，再决定正文结构。每个候选论点按 `decisiveness / controversy / reader_friction / dependency` 选择 BRIEF/NORMAL/DEEP 展开尺度。理由已经充分且新增内容不再增加证明力、反方排除力或可接受度时停止。

内部 Issue/Element/Rule/Evidence 结构默认只作为隐藏骨架；最终正文按目标、争议和论点依赖重组。重要反方或庭审中新信息改变核心论点时，必须重新规划结构，而不是在旧稿末尾补丁式追加。
