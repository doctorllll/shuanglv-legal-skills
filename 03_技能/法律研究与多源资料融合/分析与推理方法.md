# 法律研究与多源资料融合——分析与推理方法

法律研究的目的不是“搜到资料”，而是把一个法律问题转化为可验证的规范、案例、实践与解释，并明确每类信息的角色、证据边界和未解决问题。

## 1. 问题构造

把用户问题拆成决定结论的法律子问题，并同步记录需要进一步核验的事实前提。研究中发现新规则、实践信号或决定性事实后，允许重构问题树。

## 2. Source Discovery 与 Source Evaluation 分离

搜索引擎、数据库、公众号、知识库只负责发现候选材料。候选材料必须再判断发布主体、内容性质、原始性、时间/地域、可核验性、专业权威性、规范效力、事实证明力和当前用途。

不要用“来自官网/公众号/数据库”代替来源评价。

## 3. SourceRole 分层

将来源按当前用途至少区分为 `FORMAL_NORM / OFFICIAL_CASE / JUDGMENT / OFFICIAL_INTERPRETATION / PRACTICE_SIGNAL / SCHOLARLY_VIEW / PROFESSIONAL_ANALYSIS / RESEARCH_LEAD`。

研究综合时先问“它能回答什么”，再问“它权威到什么程度”。正式法源、官方解释、实践信号、理论观点可以同时重要，但不能互相冒充。

## 4. 规范定位

现行法判断优先回到正式、可核验的规范文本，检查层级、时间、地域、主体、特别规则、过渡规则和引用关系。解释性材料可以帮助理解，但不替代需要核验的正式规范。

## 5. 案例分析

案例不只记录裁判结论，应提取：决定性事实、争点、适用规则、裁判理由、程序位置、与当前任务相同和不同之处、可用于支持还是限制何种命题。

官方公众号/网页发布的原创典型案例，经主体和原始性核验后可以作为官方案例来源；二次摘录则继续追溯原文。

## 6. 类比与区别

类比的核心是比较决定性事实和法律问题，不是关键词相似。遇到结论相反的案例，优先寻找差异事实、规则版本、法院层级、程序背景、证据结构或裁判理由差异。

## 7. Research Ladder

检索按缺口递进，而不是按平台罗列：直接命中 → 要件/事实拆解 → 类案扩展 → 引文滚雪球 → 官方解释/实践信号/理论与专业分析。进入下一层要有明确触发原因。

## 8. 多源综合

对不同来源形成：共同点、冲突点、角色差异、权威差异、效力差异、时间差异和适用边界。不得通过简单多数表决决定法律结论。

特别注意：高专业权威性不等于高规范效力；高规范效力也不意味着某个材料足以回答所有实务问题。

## 9. 反向研究

重要结论必须主动寻找：反向案例、例外、限制性规则、不同地区/法院实践、更新的上位来源和可能推翻当前判断的事实条件。“没有检索到”不等于“不存在”。

## 10. 推理形成

把研究结果回写到当前 Issue，形成“问题—规范—案例—司法实践—解释/理论—适用—反方—结论—缺口”。不是每项研究都需要所有层次，只保留对当前问题有信息增益的材料。

## 11. Search Saturation

停止不是因为“已经搜了很多”，而是当前任务的主要问题、正式规范、关键案例、必要实践/解释、反向路径和重要例外达到合理覆盖，新一轮检索的信息增益明显下降。达不到时标记 `INCOMPLETE / BLOCKED / HUMAN_REVIEW_REQUIRED`。

## 12. 交付物适配

研究底稿与正式输出分离。类案检索报告强调检索范围、样本、矩阵和可比性；研究备忘录强调问题—规则—分析—结论；法规沿革强调版本与时间；趋势分析强调样本边界和分歧。

最终格式优先尊重用户/事项已保存的合法模板与写作习惯，系统默认只在没有用户覆盖时生效。

## 溯源要求

所有重要专业判断同时适用《全链路溯源规范》。正式交付中的重要命题应能够反向关联上游 Source / Rule / Case / Argument / Finding 等对象。

## 跨模块交接与回填

法律研究作为辅助技能调用时，以 `ResearchRequest` 为边界。研究结果应说明哪些原假设获得支持、哪些受到限制、哪些事实会改变规则适用、哪些 Argument / Finding 需要重检以及是否需要 WriteBackEvent。
