# 法律研究与多源资料融合——分析与推理方法

法律研究的目的不是“搜到资料”，而是把一个法律问题转化为可验证的规则、案例和论证，并明确研究边界与未解决问题。

## 1. 问题构造

把用户问题拆成决定结论的法律子问题，并同步记录需要进一步核验的事实前提。研究中发现新规则或决定性事实后，允许重构问题树。

## 2. 规范定位

优先寻找原始、权威和当前有效来源，检查层级、时间、地域、主体、特别规则、过渡规则和引用关系。二手资料用于发现线索，不代替需要核验的原始依据。

## 3. 案例分析

案例不只记录裁判结论，应提取：决定性事实、争点、适用规则、裁判理由、程序位置、与当前任务相同和不同之处、可用于支持还是限制何种命题。

## 4. 类比与区别

类比的核心是比较决定性事实和法律问题，不是关键词相似。遇到结论相反的案例，优先寻找差异事实、规则版本、法院层级、程序背景或裁判理由差异。

## 5. 多源综合

对不同来源形成：共同点、冲突点、权威差异、时间差异和适用边界。不得通过简单多数表决决定法律结论。

## 6. 反向研究

重要结论必须主动寻找：反向案例、例外、限制性规则、更新的上位来源和可能推翻当前判断的事实条件。“没有检索到”不等于“不存在”。

## 7. 推理形成

把研究结果回写到当前 Issue，形成“问题—规则—案例—适用—反方—结论—缺口”。需要类比、体系解释、目的解释或其他方法时，明确其法律用途和边界。

## 8. 停止与不确定性

研究停止不是因为“已经搜了很多”，而是当前任务的主要问题、权威来源、反向路径和重要例外已经达到合理覆盖，或者明确记录了权限、来源或事实限制。不能达到时标记 `INCOMPLETE / BLOCKED / HUMAN_REVIEW_REQUIRED`。


## 溯源要求

本技能的所有重要专业判断同时适用《全链路溯源规范》：事实应回到材料/证据和来源定位；法律规则和案例应回到权威来源及具体位置；核心分析应形成可审计的规则—事实—证据—理由链；正式交付中的重要命题应能够反向关联上游 Finding / Argument / Fact / Rule / Case 等对象。无法完成溯源时，应降低结论强度、披露限制或阻断正式交付。

## 跨模块交接与回填

法律研究在作为辅助技能调用时，应以 `ResearchRequest` 对应的具体业务问题为边界。研究完成后优先返回可被业务技能直接使用的 `LegalRule / CaseCard / SourceCard / ResearchResult`，并说明：

- 哪些原假设获得支持；
- 哪些原假设受到限制或被否定；
- 哪些事实会决定规则是否适用；
- 哪些 `ArgumentRecord / Finding` 需要重新检查；
- 是否需要生成 `WriteBackEvent`。

研究结果不应作为一篇孤立报告结束；如果它改变原业务分析，应触发回写。

## 权威图谱与类案矩阵

重要研究除 ResearchResult 外，按需要形成 AuthorityMap，说明不同规范、特别规则、案例和解释材料在当前 Issue 中的作用、时间和限制。案例对结论具有实质影响时形成 CaseMatrix，至少比较决定性事实、相似点、区别点、反向因素和原文定位。
