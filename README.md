## 一、这是什么

**爽律 Skill｜律师专业工作流系统** 是一套面向律师专业工作的 Agent Skills 工作流系统。

用户在已经加载本系统的 Agent 中，可以直接说：

> **"调用爽律来做。"**

系统会根据任务自动判断应使用哪个主技能，并在必要时组合其他辅助技能完成工作。

爽律 Skill 的目标不是替律师"自动给答案"，而是把律师日常工作中应当完成的**分析步骤、质量控制、对抗性审查、风险提示和交付要求**，固化成可调用的专业工作流程。

它有几个刻意的设计取向：

- **律师工作流，而不是裁判者流程**——从律师的角色、阶段和任务出发组织工作，不把法院审理步骤原样当作律师流程；
- **事实、陈述、推断、未知必须分层**——不把客户陈述未经核验地写成确定事实；
- **重要法律依据必须核验现行有效性**——不静态硬编码法条，不凭模型记忆下重大结论；
- **重要任务必须做第二遍对抗性审查**——主动找不利事实、反向证据、对方最强主张和会让结论翻转的假设；
- **重大决定留给律师和用户**——认罪认罚、起诉撤诉、放弃权利、签署重大合同、对外提交等由人决定；
- **平台无关**——不写死某个 Agent 平台的目录结构，只要求把 `SKILL.md` 注册为入口、把"爽律"设为调用别名。

## 三、怎么使用

最简单的方式，是直接说明任务并调用爽律 Skill；实际调用时可以简称"爽律"，例如：

- "调用爽律审查这份合同。"
- "调用爽律分析这套刑事卷宗。"
- "调用爽律研究这个法律问题。"
- "调用爽律帮我整理会见材料并设计下一次会见提纲。"
- "调用爽律对这份法律意见做一轮对抗性审查。"

用户不需要知道内部具体有哪些技能，也不需要手工选择技能。系统运行逻辑大致为：

```text
理解任务
→ 判断输入是否可靠
→ 选择主技能
→ 必要时组合辅助技能
→ 执行专业工作流
→ 对重要任务进行对抗性审查
→ 判断是否需要律师复核或用户明确授权
→ 按要求形成交付物
→ 复杂任务形成项目执行说明书
```

三个端到端示例见 [`04_使用示例/`](04_使用示例/)：[刑事阅卷](04_使用示例/01_刑事阅卷示例.md) · [合同审查](04_使用示例/02_合同审查示例.md) · [复杂法律研究](04_使用示例/03_复杂法律研究示例.md)。

## 四、安装

### 通用原则

作者对"安装成功"的定义（见 [`00_使用与调度/安装与调用说明.md`](00_使用与调度/安装与调用说明.md)）是同时满足四个条件：

1. 当前 Agent 能访问**完整**的爽律 Skill 系统；
2. 当前 Agent 能把 `SKILL.md` 或《爽律 Skill入口》作为系统入口；
3. 用户使用调用别名"爽律"时能够路由到该入口；
4. 入口可以继续读取内部各业务技能和公共规范（`00`–`04` 目录）。

因此本仓库**不拆分**、**不删减**：把整个仓库作为一个目录交给 Agent 即可。

### 常见平台的默认位置

以下路径为各平台常见的个人级 skills 目录，以各平台官方文档为准：

| 平台 | 放置位置 | 说明 |
|---|---|---|
| Claude Code | `~/.claude/skills/shuanglv-legal-skills/` | 项目级可放 `.claude/skills/` |
| Codex CLI | `~/.codex/skills/shuanglv-legal-skills/` | |
| Hermes Agent | `~/.hermes/skills/shuanglv-legal-skills/` | |
| OpenClaw | 工作区 `skills/shuanglv-legal-skills/` | |
| Cursor / Trae / 其它 IDE Agent | 作为项目目录或规则文件加载 | 在系统指令中注册别名，见下 |
| Coze / Dify / 企业知识库类平台 | 作为"项目文件 / 知识文件 / Workspace Instructions"整体上传 | 选择能让 Agent **在执行时稳定读取完整目录**的机制 |

以 Claude Code 为例：

```bash
git clone https://github.com/doctorllll/shuanglv-legal-skills.git ~/.claude/skills/shuanglv-legal-skills
```

### 平台不能自动识别入口时

v0.33 的 `SKILL.md` 是纯 Markdown 入口，尚未附带 YAML frontmatter（`name` / `description`），部分平台可能不会把它自动列为可触发技能。此时按作者《安装与调用说明》第五节的做法，在平台的系统指令 / 项目规则（如 `CLAUDE.md`、`AGENTS.md`）中加入一句：

> 当用户说"调用爽律""用爽律做""用爽律处理"时，读取 `<安装路径>/SKILL.md` 并按其中规则执行。

为各平台补充稳定的自动发现元数据（frontmatter）已列入路线，见[第十节](#十版本状态与路线)。

### 安装时不要做什么

- 不要只安装某个子技能却仍声称"已经安装完整的爽律 Skill"；
- 不要为了适配某个平台修改法律业务规则本身；平台适配应只修改入口和能力声明。

## 六、重要风险提示

### 1. 敏感案件和敏感材料应优先脱敏

真实案件材料可能包含：

- 当事人、证人、被害人等个人信息；
- 身份证号、电话号码、住址、银行卡号等敏感信息；
- 客户秘密、商业秘密；
- 未公开的侦查、诉讼或交易材料；
- 其他依法或依职业规范需要谨慎处理的信息。

在将材料提供给 AI、第三方模型、OCR、语音转写、云盘、外部 API 或其他外部服务前，应根据案件性质和使用环境进行风险判断。

**对敏感案件，原则上应先做必要脱敏，并遵循"最小必要"原则，只提供完成当前任务确实需要的内容。**

如当前任务可以使用本地、私有或用户自行控制的环境完成，应优先考虑风险更低的处理方式。

### 2. 不要因为配置了 API 或工具，就默认可以上传案件材料

API Key、账号权限或工具可用，只说明技术上能够调用，并不代表已经取得了把当前案件材料发送给第三方的授权。

涉及外部服务时，应先确认：将向谁发送；发送哪些材料；用于什么目的；是否存在日志、缓存、留存或跨境等风险；是否已经取得必要授权。

### 3. 爽律 Skill 只是专业辅助工具，不能代替律师人工判断

爽律 Skill 可以帮助完成材料整理、事实和证据分析、法律研究、工作方案比较、风险提示、文书起草、对抗性审查、质量控制。

但其输出仍可能存在：事实理解错误、信息遗漏、法律更新不及时、案例适用偏差、推理偏差、工具识别错误、AI 幻觉。

**任何拟对外使用、提交、签署或据以作出重大决定的内容，都应由具备相应专业能力的律师进行最终复核。**

### 4. 系统输出不当然构成正式法律意见

爽律 Skill 的分析、清单、草稿、风险提示和法律研究结果，原则上均属于专业工作辅助成果。是否构成律师正式法律意见，应根据委托关系、材料完整程度、事实核验情况、法律研究充分程度、律师人工复核、正式签发程序另行判断。

### 5. 重要法律依据应核验当前有效性

法律、司法解释、规范性文件、案例和监管规则可能发生修改、废止、失效或适用范围变化。涉及正式法律判断时，应尽量核验当前有效文本、生效和失效时间、过渡规则、适用法域、与案件行为发生时间的对应关系。**不得仅凭模型记忆作出重大法律结论。**

### 6. 默认面向中国大陆法律实务

本系统目前主要围绕中国大陆法律实务工作方式设计。涉及香港、澳门、台湾地区、外国法、国际法或其他法域时，应重新确认适用的法律体系、法律职业规则、案例效力和程序前提，不应直接套用中国大陆法律工作的默认假设。

## 七、人工判断与责任边界

爽律 Skill 可以提供分析和建议，但以下事项原则上应由律师或用户作最终决定：

- 是否认罪、认罚；
- 是否起诉、撤诉、上诉；
- 是否放弃重要权利；
- 是否接受和解及核心和解条件；
- 是否签署重大合同；
- 是否承担重大商业风险；
- 是否对外发送或提交正式法律文件；
- 是否向第三方提供敏感案件材料；
- 其他可能产生重大法律后果的决定。

系统不应冒充律师、客户或其他主体自动作出此类最终意思表示。完整规则见 [`00_使用与调度/人工决策与升级矩阵.md`](00_使用与调度/人工决策与升级矩阵.md)。

## 八、对抗性审查与复杂事项的续接

**对抗性审查。** 对于重要任务，爽律 Skill 在形成初步结论后，应主动进行第二遍审查：有没有遗漏不利事实；有没有反向证据；有没有不同法律解释；有没有更高权威或更新的来源；对方最强的主张是什么；哪个事实或假设变化后会使结论翻转；当前风险是否只是因为信息不足而被低估。发现重要问题后，应修正原结论，而不是仅写一句"已复核"。统一规范见 [`00_使用与调度/统一对抗性审查规范.md`](00_使用与调度/统一对抗性审查规范.md)。

**项目执行说明书。** 对于多文件、多轮或需要后续继续的事项，爽律 Skill 可以生成《项目执行说明书》，记录：收到了哪些材料；实际审阅了哪些材料；已经做了什么；形成了哪些阶段性分析；产生了哪些文件；哪些事项仍未解决；下一步从哪里继续。**"收到材料"不等于"已经审阅"。** 模板与规范见 [`00_使用与调度/`](00_使用与调度/)。

## 九、参与共创

本仓库的目标是把爽律 Skill 做成一个**由执业律师和 Agent 开发者共同维护**的专业工作流库。欢迎：

- **反馈问题**：专业规则有误、流程不顺、门控过严或过松、某个平台上跑不起来——请开 [Issue](../../issues/new/choose)；
- **提出提案**：新技能、新业务模块、新数据结构、新示例——先开 Issue 讨论方向，再动手；
- **提交 PR**：修订文字、补充检查清单、完善 schema、修复示例——请先阅读 [CONTRIBUTING.md](CONTRIBUTING.md)。

评审分两层：**仓库维护者**负责结构、格式、脱敏与平台适配的初审；**涉及法律业务规则的改动由作者终审**。合并后按版本记录进 [CHANGELOG.md](CHANGELOG.md)。

几条铁律，PR 里请自检：

- 不出现任何真实案号、当事人、身份证号、手机号、地址、案件文件名——示例一律用"张三 / 李四 / （2024）粤0XXX民初XXXX号"这类占位符；
- 不为适配某个平台去改法律业务规则本身；
- 说明正文统一用"爽律 Skill"，只有用户调用示例里才单用"爽律"；
- 新增技能必须同步更新 `manifest.json`、《技能总览》《技能调度规则》和本 README 的技能表。
