# Advisory｜法律顾问与专项分析 Domain Extension

`unit_id: unit.domain.advisory`

**Scope：** Thin advisory-specific framing/output delta. It does **not** by itself constitute a complete long-term outside-counsel operations system, recurring management-reporting engine, CRM/project-management workflow or mature dedicated correspondence platform; those capabilities may be composed only when separately implemented and verified.

## Trigger
- Directive/goal asks advisory decision framing, options/recommendation/action plan or executive/client-ready advice.

## Negative Trigger
- Document title such as “法律意见书” appears in a FORMAT_ONLY task.
- Shared reasoning/composition alone fully owns the task.

## Essential Procedure
1. Frame client objective/decision.
2. Present options and recommendation.
3. Translate into action plan/executive delivery.
4. Avoid duplicating shared research/reasoning/composition.

## Deepening Conditions
- Long-term advisory operation or correspondence context materially changes advice.

## Exit Sufficiency
- Decision-ready advisory delta is complete.

## Professional Results
- objective/decision frame
- option matrix
- recommendation/action plan
- executive delivery delta


## Domain-Specific Professional Method

## 一、这个技能解决什么问题

这个技能不是“把法条整理成一份法律意见书”，而是帮助客户完成：**问题澄清 → 事实基础 → 法律分析 → 风险/机会 → 方案比较 → 律师建议 → 客户决定 → 行动计划。**

它适合日常法律咨询、专项分析、管理层决策支持和正式法律意见等场景。

## 二、主流程

```text
识别客户表面问题和真正目标
→ 明确本次工作范围
→ 区分已知事实、陈述事实、争议事实、未知事实和假设
→ 建立问题树
→ 调用法律研究
→ 将法律规则适用于事实
→ 同时识别风险和有利因素
→ 设计多个可行方案
→ 用统一维度比较方案
→ 分开表达法律结论、律师建议和客户决定
→ 形成行动计划
→ 根据需要制作正式意见或内部备忘
```


## 三、执行步骤速查表

| 步骤 | 要做什么 | 主要方法 | 阶段产物 |
|---|---|---|---|
| 1. 重构问题 | 把表面提问变成真正决策问题 | 客户目标、读者、决策场景识别 | 重新定义的问题 |
| 2. 事实基础 | 分开已知、陈述、争议、未知和假设 | 事实状态管理 | 事实基础表 |
| 3. 问题树 | 拆分决定结论的子问题 | 实体/程序/证据/监管/实施分层 | 问题树 |

## 四、重新定义问题

客户提问经常不是法律分析真正应该回答的问题。例如“这个合同能不能签”，可能实际包含：是否存在无效风险；哪些条款可修改；哪些风险只能商业接受；有没有替代结构；是否需要补充前提条件或尽调。

因此不能机械回答表面措辞，而要先形成“重新定义后的问题”和客户真正希望作出的决定。

## 五、事实基础

法律意见最严重的错误往往来自事实基础错误。应区分：已核验事实、客户或第三方陈述、争议事实、推断事实、未知事实，以及经用户明确允许后才能采用的假设。

每个假设都应说明为什么需要、假设内容是什么、如果不成立哪些结论会变化。不能为了让文稿顺畅而默默补全缺失事实。

**默认不允许用未披露假设填补决定性事实缺口。**只有用户明确允许工作假设，或当前任务本身允许以明确标注的条件假设推进时，才能继续；否则保持 UNKNOWN / INCOMPLETE 并说明所需材料。

## 六、问题树

复杂咨询要拆成不同类型的问题：实体法律、程序、证据、监管、事实核验、商业或实施问题，并区分主问题和子问题。优先处理会真正改变决策的关键问题，不平均分配篇幅。

## 七、法律研究与分析

研究阶段调用“Research Capability”。分析逻辑通常是：问题 → 相关事实 → 适用规则 → 规则解释或要件 → 适用于事实 → 反向观点 → 阶段性结论。

重要问题还要回答：对方可能怎样理解；是否存在不同观点；哪些事实变化会改变结论；当前研究是否有缺口。研究不完整时，这种限制必须传递到最终意见。

## 八、风险和机会同时分析

法律顾问不能只“提示风险”。每个重要问题可以记录风险场景、发生可能性（定性）、影响、可控制程度、缓释措施和剩余风险；同时记录有利规则、有利事实、可以争取的空间和替代路径。

没有可靠统计基础时不生成伪精确概率。

风险结论不能止于“不能做 / 有风险”。在合法且与客户目标相关的范围内，应继续检查是否存在**合法替代结构、附条件方案、补救措施、补充材料或降低风险的可执行路径**；确无可行路径时再明确说明。

## 九、多方案比较

存在多个路径时，使用同一组维度比较，例如：法律可行性、事实前提、执行步骤、优缺点、法律风险、实施风险、时间、成本、可逆性和对未来争议的影响。

这样客户看到的是一个可决策的比较，而不是互相不可比的“方案一、方案二”。

## 十、三层决策边界

必须严格区分：

1. **法律结论**：法律和现有事实支持到什么程度；
2. **律师建议**：结合风险和客户目标建议选择什么方案；
3. **客户决定**：是否接受某个商业、管理或战略风险。

Agent 不能把客户决定伪装成法律结论，也不能替客户作重大商业选择。

## 十一、行动计划

好的意见不应停在“存在风险”。应尽量转化为：要补什么材料、由谁完成、先后顺序、何时完成、是否需要谈判/通知/备案/申请、什么条件不满足时切换备选方案、哪些节点需要再次法律复核。

## 十二、正式意见

正式法律意见通常说明：委托目的、审阅材料、事实基础、重要假设、问题清单、法律依据、分析、反向观点、结论、风险、可行方案、律师建议、行动计划以及适用范围和时间边界。格式和排版交给“Composition / Review Capability”。

## 十三、人工复核门

客户明显要求预设答案、重大事实只能依赖假设、法律存在明显争议、多方案涉及重大商业取舍、结论可能影响重大交易/监管/诉讼、需要正式对外法律意见时，应由律师确认。

## 十四、主要产出

重新定义后的问题、事实基础表、问题树、法律研究任务、分析结果、风险/机会图、多方案比较、律师建议、客户决策事项、行动计划、正式意见或内部备忘内容基础以及Resume Capsule（续接/交接摘要）（仅续接/交接/归档需要时）。
