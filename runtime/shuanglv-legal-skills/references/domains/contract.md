# Contract｜合同与交易 Domain Extension

`unit_id: unit.domain.contract`

**Scope：** Contract-specific delta only.

## Trigger
- Directive/goal asks substantive contract drafting/review/transaction/risk/negotiation analysis.

## Negative Trigger
- FORMAT_ONLY contract task.
- Contract words occur only in payload unrelated to current goal.

## Essential Procedure
1. Model transaction and performance flow.
2. Stress-test clause function and failure scenarios.
3. Map obligation-evidence-remedy and coverage.
4. Preserve negotiation/signing handoff.

## Deepening Conditions
- Complex transaction architecture.
- Third-party/bidirectional breach risk.
- Negotiation or interpretation ambiguity.

## Exit Sufficiency
- Material transaction/contract risks and intended allocation are expressed.

## Professional Results
- transaction/document architecture
- contract-specific risk/coverage/negotiation delta


## Domain-Specific Professional Method

## 一、这个技能不是“挑错字”

合同文字只是交易结构、履行流程和风险分配的表达。因此正确顺序不是从第一条逐字修改，而是先理解客户代表哪一方、交易要实现什么、双方怎么履行、哪里可能失败，再决定合同如何设计和修改。

## 二、主流程

```text
确认客户代表方、目标、谈判地位和工作深度
→ 识别交易结构
→ 理解或设计整个文件体系
→ 画出履行流程和权利义务地图
→ 同时模拟对方违约、我方违约、第三方/审批失败
→ 把风险场景映射为条款功能
→ 核验现行法和监管要求
→ 起草/审查/修改条款
→ 形成谈判首选和备选方案
→ 宏观—中观—微观复核
→ 实际修改合同文本并形成修订、清洁、批注和版本交接要求
→ 签署与履行交接
```


## 三、执行步骤速查表

| 步骤 | 要做什么 | 主要方法 | 阶段产物 |
|---|---|---|---|
| 1. 需求确认 | 明确代表方、交易目标、谈判地位和工作深度 | 代表方门控、客户决策边界 | 需求与约束清单 |
| 2. 交易结构 | 先判断交易如何成立和履行 | 主体、标的、对价、条件、审批、第三方依赖 | 交易结构图 |
| 3. 文件架构 | 判断需要哪些文件及其关系 | 主协议/附件/订单/交割文件层级分析 | 文件体系图 |
| 4. 履行流程 | 把交易变成逐步可执行流程 | 权利—义务—条件—确认—证据闭环 | 履行与义务地图 |
| 5. 风险推演 | 模拟交易失败的多种方式 | 对方违约、我方违约、第三方/审批失败双向模拟 | 风险场景清单 |
| 6. 条款功能 | 把风险分配变成条款 | 义务、权利、条件、救济、程序、风险分配功能分析 | 条款审查意见 |
| 7. 法律核验 | 检查强制规则和行业要求 | 现行法和特别法核验 | 法律问题清单 |
| 8. 起草/修改 | 从结构到条款再到语言并真正落到合同文本 | 增删改、重构、批注、备选文本 | 实际修订稿 + 必要修改说明 |
| 9. 谈判 | 给客户可选择的谈判空间 | 首选/备选/底线/交换条件 | 谈判问题表 |
| 10. QA与交接 | 检查全文和签署后事项 | 宏观—中观—微观复核、版本控制 | 交付稿与履行清单 |

## 四、代表方和需求门控

必须先知道代表哪一方、客户真正目标、哪些结果不能让步、哪些风险可接受、谈判地位、当前是内部样稿/谈判稿/正式签约稿，以及用户要的是起草、审查、修改、谈判支持还是终稿复核。连代表方都不知道时，不应该逐条改合同。

## 五、交易结构优先

先回答：谁和谁交易；标的是什么；谁先履行；价款和对价怎么走；交付验收如何完成；是否依赖审批、许可、融资或第三方；权利何时转移；交易失败时如何退出；是否存在更安全的替代结构。结构有重大问题时先暂停文字级修改。

## 六、文件架构

复杂交易往往包含主协议、框架、订单、附件、技术规范、价格表、交割文件、补充协议等。要检查文件优先级、定义一致性、同一事项是否冲突，以及关键权利义务是否掉在文件缝隙里。目标是让文件结构与交易结构一致。

## 七、履行流程与义务地图

按“步骤—行动人—义务—前提—交付物—确认—时间—付款—证据—失败后果”拆解履行。重点检查：权利与义务是否对应；义务与责任是否闭环；条件由谁确认；以后能否证明已经履行。

## 八、双向风险场景推演

至少模拟：对方违约、我方违约、第三方不配合、审批失败、市场变化、验收争议、提前终止、证据/确认缺失。对每个风险问：合同是否已有处理规则；风险由谁承担；有没有通知、补救、宽限、解除、赔偿、担保或争议解决机制；这些机制能否执行。

同时检查是否存在**责任真空、循环义务、相互矛盾的触发条件或一方实际上无法控制的绝对结果义务**。风险控制不能只追求“对我方最强”：若修改使交易明显不可谈判、不可履行或破坏核心交换，应把保护强度与交易可实现性一起呈现给客户决定。

## 九、条款功能方法

先识别条款功能，再看具体措辞：义务、权利、单方决定权、陈述、保证、条件、定义、程序、救济、风险分配。每个重要条款检查“谁、做什么、何时、标准、条件、例外、对应权利、违约后果、证明方式、与其他条款冲突”。外国合同表达只能作为功能或语言参考，法律效果必须按适用法核验。

## 十、现行法核验

结合交易检查主体资格、标的合法性、强制性规定、审批许可、成立生效、格式条款、违约责任、解除、赔偿、担保以及数据、知识产权、劳动、监管等专项规则。通用合同规则不能替代行业特别法。

## 十一、起草、审查和谈判

**修改合同必须修改合同。** 用户明确要求“修改、帮我改、优化这份合同、直接改合同”等时，修改后的合同文本是 REQUIRED 交付物，报告只是辅助。合同审查默认也应把成熟的修改建议落实到文本中；只有用户明确要求“先别改”“只出风险报告/审查意见”时才采用 report-only。


推荐顺序：交易结构 → 文件架构 → 履行和风险 → 条款 → 语言。模板只能作为起点。商业参数未确定时，应明确留给客户决定。

谈判争点应形成：我方利益、对方关切、首选立场、首选文本、备选文本、最低可接受方案、让步交换条件、剩余风险和决策人。

## 十一A、履约可操作性、可证明性与争议解释测试

重要履行义务应尽量形成“触发条件—行动主体—内容/标准—期限—确认—证据—付款/对价—违约后果—退出”的闭环。付款结构原则上应与可验证的履约成果相匹配，但仍以具体交易、谈判地位和客户目标为准，不机械追求所谓最安全付款方式。

对关键条款再从未来争议视角进行解释压力测试：不只看词句，还要看条款体系、交易目的、缔约背景、版本演变、履行行为和可证明的交易习惯。若合理解释存在分叉，应优先消除歧义而不是寄希望于未来解释。

## 十一B、条款覆盖地图

按交易需要检查“身份与解释—交易与对价—履行与流程—保障与治理—异常与救济”五类功能。它是遗漏检查工具，不是固定模板。

## 十二、质量检查与履行交接

宏观看交易结构；中观看章节、权利义务、条件和责任；微观看数字、日期、主体、附件和术语；法律层面核验现行规则；交付层面检查修订稿、清洁稿、批注和版本。

签署后还要明确生效条件、交割资料、关键履行节点、续期/解除期限、通知义务和证据留存。长期提醒交给外部项目系统，本模块负责本次交接。

## 十三、主要产出

事项核心概要、核心交易/履行示意图（适用时）、交易结构图、文件体系图、履行流程图、权利义务地图、风险场景、条款功能审查、法律核验清单、合同审查意见、**实际修改后的合同文本**、必要修改说明、谈判问题表、首选/备选条款、修订/清洁/批注交付要求、签署与履行交接清单和Resume Capsule（续接/交接摘要）（仅续接/交接/归档需要时）。

## 风险场景推演规则

对每个关键交易节点至少模拟：正常履行、对方迟延/拒绝、我方迟延/不能履行、第三方/审批失败、提前终止。
每个场景输出：trigger / affected 目标 / 影响 / controllability / current bearer / prevention / allocation / response / remedy / 证据 / clause link / 客户 决策。
无可靠数据时不得生成主观概率百分比。

## 合同审查检查清单

1. 代表哪方？→ 不清楚先核实。
2. 客户目的/非谈判项？→ 不清楚先沟通。
3. 谈判地位/修改尺度？→ 决定 preferred / 备选。
4. 交易结构是否可行？→ 否：停止文字精修。
5. 文件架构是否匹配交易？→ 否：先重构。
6. 履行流程完整？→ 建 Obligation 图。
7. 正常/异常场景覆盖？→ 建 风险 Scenario。
8. 条款功能、法律效果、解释风险、内部一致性？→ 审阅/Revise。
9. 商业参数？→ 客户决定。
10. REVIEW/REVISE 是否真正修改合同文本？→ 报告不得代替。
11. 独立复核 → 差异稿/Clean/批注/版本 → Signing Handoff。
